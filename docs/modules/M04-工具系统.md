## 0. 本模块在项目中的位置

M03 的 Loop 已经会"调工具"了，但工具从哪来、怎么声明、怎么安全执行？本模块回答三问：

```text
① 声明：模型怎么知道有哪些工具、参数长什么样？  → ToolSpec + JSON Schema
② 执行：工具跑飞了/读到大文件/越界写路径怎么办？ → 沙箱（超时/截断/路径防护）
③ 并发：Agent 和用户同时改一个文件怎么办？       → 乐观锁
```

**交付后状态**：`builtin/` 里 5 个工具可被模型自主选用；写文件带乐观锁保护；任何工具超时/异常都变成干净的错误 Observation。

## 1. 知识点详解

### 1.1 Function Calling 机制全景

**① 原理**

一次完整的工具协议往返：

```text
1. 客户端随请求发送 tools: [{type:"function", function:{name, description, parameters: JSONSchema}}]
2. 模型不执行任何东西——它输出 tool_calls: [{id, name, arguments:"<json字符串>"}]
3. 客户端（你）本地执行真实函数
4. 把结果作为 {"role":"tool", tool_call_id, content} 回传
5. 模型基于 Observation 继续生成
```

**模型从头到尾没有执行能力**——它只是"建议"了一次函数调用。执行、安全、超时、重试全是客户端的责任。这个认知是工具系统一切设计的起点。

**JSON Schema 是工具的"类型签名"**：

```python
ToolSpec(name="read_file",
  description="读取项目内文本文件。返回内容与 mtime。",
  parameters={                       # 这就是 JSON Schema（draft 2020-12 子集）
    "type": "object",
    "properties": {"path": {"type": "string", "description": "项目相对路径"}},
    "required": ["path"], "additionalProperties": False}})
```

description 质量直接决定模型选对工具的概率——"描述是给模型看的提示词"这个观念必须有。

**② 演进**：ReAct 正则解析时代（工具用文本协议描述，模型抄格式常抄错）→ 2023.6 OpenAI Function Calling（结构化输出 + 训练过的专用能力）→ 并行工具调用/strict mode（schema 约束的强保证）→ MCP（跨应用的工具生态标准化，M05）。分界线：**FC 解决"单应用内模型怎么调函数"，MCP 解决"工具跨应用复用"**。

**③ 最小案例** `lab/m04/fc_roundtrip.py`——裸看协议往返（续 M02 的 raw 客户端）：

```python
tools = [{"type": "function", "function": {
    "name": "get_weather", "description": "查询城市天气",
    "parameters": {"type": "object",
                   "properties": {"city": {"type": "string"}},
                   "required": ["city"]}}}]

resp = httpx.post(URL, json={"model": M, "messages":
    [{"role": "user", "content": "北京今天热吗？"}], "tools": tools}).json()
tc = resp["choices"][0]["message"]["tool_calls"][0]
print(tc["function"]["name"])     # get_weather —— 模型"建议"的调用
print(tc["function"]["arguments"])  # '{"city": "北京"}' —— 注意是 JSON 字符串！

WEATHER = {"北京": "38°C 晴"}
follow_up = [*messages, resp["choices"][0]["message"],
    {"role": "tool", "tool_call_id": tc["id"],
     "content": WEATHER[json.loads(tc["function"]["arguments"])["city"]]}]
# 再发一次请求 → 模型回答"北京 38 度，很热"
```

**④ 易错点**
- `arguments` 是**字符串**不是对象，必须 `json.loads`；且可能是不完整 JSON（流式分片，M02 聚合器已处理）
- `additionalProperties: False` + 完整 required 能显著降低幻觉参数；strict 模式下是硬约束
- description 写"实现细节"（如"内部用 aiofiles"）毫无意义——要写**何时该用/何时不该用**
- 工具数量不是越多越好：30+ 工具同发会让选择准确率下降（M15 子代理工具过滤正是解法）

### 1.2 注册表与 Schema 自动生成

**① 原理**：装饰器注册 + pydantic 自动生成 Schema，"定义即注册即声明"：

```python
@register_tool(readonly=True, risk="low")
class ReadFileTool(BaseTool):
    """读取项目内文本文件。"""
    class Params(BaseModel):          # pydantic 模型 = JSON Schema 的唯一事实源
        path: str = Field(description="项目相对路径，如 'scripts/player.gd'")
    async def run(self, path: str) -> ToolResponse: ...
```

注册表提供三个视图：`tool_specs()`（喂模型的 FC 声明）、`get(name)`（Dispatcher 执行用）、`filter(tags)`（子代理/M13 模式按需裁剪）。**一份定义三处复用**——手写 Schema 字符串与函数签名漂移是新手最常见 bug 源，自动生成从根上消灭。

**② 演进**：手写 JSON 字符串字典 → 装饰器注册（Flask 路由同款思想）→ 类型驱动（pydantic dataclass → schema，FastAPI 同源机制——你在这里学的就是 FastAPI 的原理）→ MCP 的工具发现（运行时拉取，M05）。

**③ 最小案例**：pydantic → JSON Schema 只要一行

```python
from pydantic import BaseModel
class Params(BaseModel):
    path: str
    max_bytes: int = 4096
print(Params.model_json_schema())
# {"type":"object","properties":{"path":{"type":"string"},...},
#  "required":["path"]}  —— 直接可用作 FC parameters
```

**④ 易错点**
- pydantic 的 `title` 字段会混进 schema，部分 API 拒绝未知关键字——注册时做一次 schema 清洗
- 工具重名（本地工具 vs MCP 桥接工具）：注册表要支持命名空间前缀 `mcp__godot__read_scene`
- 装饰器类注册 vs 函数注册选一个统一，混用导致两套元数据抽取逻辑

### 1.3 ToolResponse 协议：结构化的工具结果

**① 原理**：工具永远不抛异常给 Loop，而是返回统一的响应对象：

```python
@dataclass
class ToolResponse:
    ok: bool
    data: Any = None                  # 结构化数据（给程序消费）
    summary: str = ""                 # 给模型看的文本渲染（Observation）
    error: ToolError | None = None
    artifacts: list[Artifact] | None = None   # diff/文件引用等前端要渲染的东西
```

关键设计是 **summary 与 data 分离**：模型读 summary（人话），前端读 artifacts（渲染 Diff 卡片）。一个工具调用同时喂饱两个消费者——对应 M03 事件流的双前端哲学。

输出预算：summary 默认截断到 2000 字符并附 `...[truncated 15KB]`——大结果（headless 日志）直接塞会把上下文撑爆（M07 会再做摘要，这里先兜底）。

**② 演进**：函数直接 return str（无法区分成败/无法结构化）→ 抛异常（中断循环）→ 协议对象（hello-agents 的 ToolResponse 同款思想）。"错误也是数据"是 Agent 工程反复出现的母题。

**③ 最小案例**：错误渲染

```python
def render_for_model(self) -> str:
    if self.ok:
        return self.summary
    return f"[工具 {self.error.tool} 失败: {self.error.kind.value}] {self.error.message}\n" \
           f"可采取的行动: {self.error.hint or '检查参数后重试'}"
# 模型收到的 Observation 示例：
# [工具 write_file 失败: conflict] 文件已被外部修改 (mtime 不匹配)
# 可采取的行动: 重新 read_file 获取最新内容后再修改
```

**④ 易错点**
- error.hint 值得写：给模型的"纠错指引"能把重试成功率提高一截（它真的会照着做）
- 二进制结果（截图/音频）绝不能进 summary——存 MinIO/本地路径，Observation 只放路径
- ok=True 但业务空结果（检索零命中）与 ok=False 要区分，模型对两者的后续策略不同

### 1.4 沙箱：超时、截断、路径越界防护

**① 原理**：Dispatcher 执行工具前后的三道闸：

```text
执行前：路径规范化 + 项目根白名单校验（防 path traversal：../../etc/passwd）
执行中：asyncio.wait_for(timeout)（读 10s/写 30s/headless 120s 分级）
执行后：输出截断策略（头部 N 字节 + 尾部 N 字节 + 中间省略标记）
```

路径越界的经典攻击：`read_file(path=".git/config")`、`path="res://../../.ssh/id_rsa"`。防御：`(root / path).resolve()` 后强制 `is_relative_to(root)`，否则直接 ToolResponse 失败（不抛异常）。`.git/`、`*.env` 等敏感路径再叠一层 denylist（permissions.yaml 的雏形，M09 展开）。

**② 演进**：裸 await（工具卡死全卡死）→ wait_for 超时 → 输出截断 → 路径防护 → （生产级再进阶：进程隔离/容器沙箱/权限系统）。本模块做前四层，第五层 M09。

**③ 最小案例**

```python
def resolve_in_root(root: Path, rel: str) -> Path:
    p = (root / rel).resolve()
    if not p.is_relative_to(root.resolve()):
        raise PathEscapeError(f"{rel} escapes project root")
    if any(part in DENY_PARTS for part in p.parts):   # {".git", ".env", "__pycache__"}
        raise DeniedPathError(str(p))
    return p

def truncate(text: str, head=1500, tail=300) -> str:
    if len(text) <= head + tail + 50:
        return text
    return f"{text[:head]}\n...[中间省略 {len(text)-head-tail} 字符]...\n{text[-tail:]}"
```

**④ 易错点**
- Windows 路径大小写不敏感 + 反斜杠：`resolve()` 前先统一 posix 化，否则 `is_relative_to` 判定漂移
- `wait_for` 取消后子进程可能残留（headless Godot）：要用 `Process.kill()` 显式清理
- 截断要保头保尾——错误信息常在尾部（traceback），只保头会丢关键

### 1.5 乐观锁文件编辑（并发写防护）

**① 原理**

悲观锁（先锁再改，锁期间他人等待） vs **乐观锁**（不锁，提交时校验"我读之后没人改过"，冲突则失败重试）。Agent 场景选乐观：

```text
1. read_file 返回内容 + 期望版本（mtime 或 content hash）
2. 模型生成修改，write_file(path, content, expect_hash)
3. 写前重算当前文件 hash ≠ expect_hash → 冲突失败：
   "文件已被修改，请重新读取"（模型下一轮会重读再改——自我修复）
```

为什么不用线程锁：冲突方是"用户在编辑器里手动改了文件"，**锁不住人**；且模型从读到写隔着一轮推理（几十秒），悲观锁会把所有人饿死。乐观锁用"版本校验"把跨秒级的并发变成一次可自愈的失败。

**② 演进**：无保护（后写覆盖，静默丢改动）→ 文件系统 mtime 检查（精度问题：同秒内修改检测不到）→ **content hash（SHA-256 前 16 位）**（本项目采用）→ git 原子提交/CRDT（重武器，个人项目过度设计）。

**③ 最小案例**：完整冲突流

```python
async def write_file(self, path: str, content: str, expect_hash: str) -> ToolResponse:
    p = resolve_in_root(self.root, path)
    cur = sha16(p.read_text(encoding="utf8")) if p.exists() else EMPTY
    if cur != expect_hash:
        return ToolResponse(ok=False, error=ToolError(
            kind=ErrorKind.CONFLICT, tool="write_file",
            message=f"版本冲突: 期望 {expect_hash[:8]} 实际 {cur[:8]}（文件已被外部修改）",
            hint="先重新 read_file 获取最新版本，再基于新内容重新修改"))
    backup = self.checkpoint.snapshot(p)          # M06 检查点：写前快照
    p.write_text(content, encoding="utf8")
    return ToolResponse(ok=True, summary=f"已写入 {path} ({len(content)}B)",
                        artifacts=[Artifact(type="diff", ref=str(backup))])
```

**④ 易错点**
- hash 要覆盖"内容"，mtime 只能做辅助信号（同秒写两次 mtime 相同）
- 冲突后**不要自动帮模型合并**——让模型重读重写，自动合并产生的"缝合怪"更难调试
- 快照要在写之前做（顺序错了就没有回头路），且快照本身失败要阻断写入

## 2. 接口设计（完整签名）

```python
# tools/registry.py
@dataclass
class ToolMeta:
    name: str; description: str
    readonly: bool                    # Dispatcher 分流依据
    risk: Literal["low", "medium", "high"]   # M09 权限分级依据
    tags: set[str] = set()            # 模式/子代理过滤依据

class ToolRegistry:
    def register(self, tool: "BaseTool") -> None: ...
    def tool_specs(self) -> list[dict]: ...          # FC 声明（给模型）
    def get(self, name: str) -> "BaseTool": ...
    def filter(self, *, tags=None, readonly=None) -> "ToolRegistry": ...  # 视图裁剪
    def namespaced(self, ns: str) -> "ToolRegistry": ...  # mcp__godot__ 前缀

class BaseTool(ABC):
    meta: ToolMeta
    Params: type[BaseModel]                       # pydantic 参数模型
    @abstractmethod
    async def run(self, **params) -> ToolResponse: ...

def register_tool(**meta_kwargs) -> Callable[[type[BaseTool]], type[BaseTool]]: ...

# tools/response.py
class ErrorKind(Enum):
    NOT_FOUND="not_found"; VALIDATION="validation"; TIMEOUT="timeout"
    CONFLICT="conflict"; DENIED="denied"; INTERNAL="internal"

@dataclass
class ToolError: kind: ErrorKind; tool: str; message: str; hint: str | None
@dataclass
class Artifact: type: Literal["diff","file","image","log"]; ref: str; meta: dict | None

# tools/sandbox.py
def resolve_in_root(root: Path, rel: str) -> Path: ...
def truncate(text: str, head: int = 1500, tail: int = 300) -> str: ...
async def run_with_timeout(coro, seconds: float, on_cancel: Callable | None) -> Any: ...

# tools/file_lock.py
def sha16(text: str) -> str: ...
class OptimisticFileStore:
    async def read(self, path: str) -> tuple[str, str]: ...          # (content, hash)
    async def write(self, path: str, content: str, expect_hash: str) -> ToolResponse: ...
```

## 3. 关键难点参考片段：schema 清洗

pydantic 生成的 schema 含 `title`、`$defs` 等 FC API 不接受/不一致的字段，注册时必须清洗（这个细节 90% 的手写教程漏掉，跑到真 API 才炸）：

```python
def to_fc_schema(params: type[BaseModel]) -> dict:
    schema = params.model_json_schema()
    def clean(node: dict) -> dict:
        node.pop("title", None)
        if "$defs" in schema:                      # 内联 $ref（嵌套模型）
            node.pop("$defs", None)
            defs = schema["$defs"]
            def deref(n):
                if "$ref" in n:
                    return deref(defs[n["$ref"].split("/")[-1]])
                for k, v in list(n.items()):
                    if isinstance(v, dict): n[k] = deref(v)
                    if isinstance(v, list): n[k] = [deref(x) if isinstance(x, dict) else x for x in v]
                return {a: b for a, b in n.items() if a != "title"}
            return deref(node)
        return node
    return clean(schema)
```
