## 0. 本模块在项目中的位置

**大白话**：M03 的 Loop 是"会伸手拿东西的手"，但**东西摆在哪、怎么摆、哪些能碰哪些不能碰**——那是本模块的事。它回答三个问题：

```text
① 声明：模型怎么知道有哪些工具、参数长什么样？  → ToolSpec + JSON Schema
② 执行：工具跑飞了/读到大文件/越界写路径怎么办？ → 沙箱（超时/截断/路径防护）
③ 并发：Agent 和用户同时改一个文件怎么办？       → 乐观锁
```

类比：本模块是**工具墙 + 车间安全规程**。注册表是挂工具的洞洞板（每件工具挂好标签卡片=Schema）；沙箱是车间规程（带电作业限时、碎屑要清扫、危险区拉警戒线）；乐观锁是"改图纸前先确认没人动过"的交接班制度。

**交付后状态**：`builtin/` 里 5 个工具可被模型自主选用；写文件带乐观锁保护；任何工具超时/异常都变成干净的错误 Observation。

## 1. 知识点详解（每节五段：定义 → 大白话 → 举例 → 演进 → 易错点）

### 1.1 Function Calling 机制全景

**① 严格定义**：开发者以 JSON Schema 声明工具（name/description/parameters）随请求发送（`tools` 字段）；模型**不执行任何东西**——它输出结构化"建议" `tool_calls:[{id,name,arguments}]`（arguments 是 JSON **字符串**）；客户端本地执行真实函数，把结果作为 `{"role":"tool", tool_call_id, content}` 回传；模型基于 Observation 继续生成。

**② 大白话**：模型是**咨询顾问，不是执行者**。它看了你的工具清单说"我建议调用 read_file，参数 path=enemy.gd"（写在纸条上递给你）——真正去开门拿文件的是**你**。这个认知是工具系统一切设计的起点：执行、安全、超时、重试全是客户端（你）的责任。模型从头到尾只有"建议权"，没有"执行权"。

**③ 举例**：一次完整的协议往返（`lab/m04/fc_roundtrip.py`，续 M02 的裸客户端）：

```python
tools = [{"type": "function", "function": {
    "name": "get_weather", "description": "查询城市天气",
    "parameters": {"type": "object",
                   "properties": {"city": {"type": "string"}},
                   "required": ["city"]}}}]

resp = httpx.post(URL, json={"model": M, "messages":
    [{"role": "user", "content": "北京今天热吗？"}], "tools": tools}).json()
tc = resp["choices"][0]["message"]["tool_calls"][0]
print(tc["function"]["name"])        # get_weather —— 模型"建议"的调用
print(tc["function"]["arguments"])   # '{"city": "北京"}' —— 注意是 JSON 字符串！

WEATHER = {"北京": "38°C 晴"}
follow_up = [*messages, resp["choices"][0]["message"],
    {"role": "tool", "tool_call_id": tc["id"],
     "content": WEATHER[json.loads(tc["function"]["arguments"])["city"]]}]
# 再发一次请求 → 模型回答"北京 38 度，很热"
```

**description 是给模型看的提示词**：写"何时该用/何时不该用"（"读取项目内文本文件，改代码前先用它获取当前内容与版本号"），不写实现细节（"内部用 aiofiles"）——描述质量直接决定模型选对工具的概率。

**④ 演进**：ReAct 正则解析时代（工具用文本协议描述，模型抄格式常抄错）→ 2023.6 OpenAI Function Calling（结构化输出+训练过的专用能力）→ 并行调用/strict mode（schema 约束的强保证）→ MCP（工具跨应用复用标准化，M05）。分界线：**FC 解决"单应用内模型怎么调函数"，MCP 解决"工具跨应用复用"**。

**⑤ 易错点**：
- `arguments` 是**字符串**不是对象，必须 `json.loads`；且流式下可能是不完整 JSON（M02 聚合器已处理）
- `additionalProperties: False` + 完整 required 能显著降低幻觉参数
- 工具数量不是越多越好：30+ 工具同发，选择准确率下降（M15 子代理工具过滤正是解法）

### 1.2 注册表与 Schema 自动生成

**① 严格定义**：装饰器注册 + pydantic 自动生成 Schema——"定义即注册即声明"：一个工具类同时产出①FC 声明（喂模型）②执行入口（Dispatcher 调用）③元数据（readonly/risk/tags，供分流/权限/模式过滤）。

**② 大白话**：**洞洞板管理法**。传统做法是工具定义、Schema 字符串、执行注册表**三处分开写**——改了函数签名忘改 Schema，模型就会按旧说明填参数（新手最常见 bug）。注册表把三样合并：你只写一次 pydantic 参数模型，Schema 从它自动生成、注册自动完成——**单一事实源**。这和 M02 的 `@register_provider` 是同一个思想（M00"一切皆插件"第二次落地），你在 FastAPI 里见过的"装饰器路由+类型驱动文档"也是同源。

**③ 举例**：

```python
@register_tool(readonly=True, risk="low")
class ReadFileTool(BaseTool):
    """读取项目内文本文件。"""              # ← 这个 docstring 就是 FC 的 description
    class Params(BaseModel):               # ← pydantic 模型 = Schema 的唯一事实源
        path: str = Field(description="项目相对路径，如 'scripts/player.gd'")
    async def run(self, path: str) -> ToolResponse: ...
```

注册表三个视图各喂一个消费者：`tool_specs()` 喂模型（FC 声明）、`get(name)` 喂 Dispatcher（执行）、`filter(tags/readonly)` 喂 M13 模式与 M15 子代理（**ask 模式物理上不给写工具**——工具集即能力边界，比提示词说"不要改文件"可靠一个量级）。

pydantic → JSON Schema 一行见证奇迹：

```python
class Params(BaseModel):
    path: str
    max_bytes: int = 4096
print(Params.model_json_schema())
# {"type":"object","properties":{"path":{"type":"string"},...},"required":["path"]}
```

**④ 演进**：手写 JSON 字符串字典 → 装饰器注册（Flask 路由同款思想）→ 类型驱动（pydantic→schema，FastAPI 同源——你在这里学的就是 FastAPI 的原理）→ MCP 工具发现（运行时拉取，M05）。

**⑤ 易错点**：
- pydantic 的 `title` 会混进 schema，部分 API 拒绝未知关键字——注册时清洗（§3 难点代码）
- 工具重名（本地 vs MCP 桥接）：注册表支持命名空间前缀 `mcp__godot__read_scene`
- 类注册 vs 函数注册选一个统一，混用导致两套元数据抽取逻辑

### 1.3 ToolResponse 协议：结构化的工具结果

**① 严格定义**：工具永远不向 Loop 抛异常，而是返回统一响应对象：`ToolResponse(ok, data, summary, error, artifacts)`——**summary 给模型读（Observation）、data/artifacts 给程序与前端消费**，错误也结构化（kind + message + hint）。

**② 大白话**：**标准化的工作报告单**。老板（模型）不关心你的血泪过程，只要一页纸：成没成（ok）、结论是什么（summary）、原始数据附页（data）、给客户看的图表（artifacts）、失败的原因与**下一步建议**（error.hint）。hint 是精髓——"可采取的行动：重新 read_file 获取最新内容"这种话模型**真的会照着做**，把重试成功率拉高一截。

**③ 举例**：

```python
@dataclass
class ToolResponse:
    ok: bool
    data: Any = None                  # 结构化数据（程序消费）
    summary: str = ""                 # 给模型看的文本渲染（Observation）
    error: ToolError | None = None
    artifacts: list[Artifact] | None = None   # diff/文件引用（前端渲染 Diff 卡片）

def render_for_model(self) -> str:
    if self.ok:
        return self.summary
    return f"[工具 {self.error.tool} 失败: {self.error.kind.value}] {self.error.message}\n" \
           f"可采取的行动: {self.error.hint or '检查参数后重试'}"

# 模型收到的 Observation 示例：
# [工具 write_file 失败: conflict] 文件已被外部修改 (hash 不匹配)
# 可采取的行动: 重新 read_file 获取最新内容后再修改
```

输出预算：summary 默认截断 2000 字符并附 `...[truncated 15KB]`——大结果（headless 日志）直接塞会把上下文撑爆（M07 再做摘要，这里先兜底）。

**④ 演进**：函数 return str（无法区分成败/结构）→ 抛异常（中断循环，模型失去自愈机会）→ 协议对象。"**错误也是数据**"是 Agent 工程反复出现的母题（M02 的 errors 分类、M06 的校验回填同源）。

**⑤ 易错点**：
- ok=True 但业务空结果（检索零命中）与 ok=False 要区分——模型的后续策略不同（换查询 vs 报错重试）
- 二进制结果（截图/音频）绝不进 summary——存 MinIO/本地路径，Observation 只放路径
- error.hint 值得写：模型的纠错成功率差异肉眼可见

### 1.4 沙箱：超时、截断、路径越界防护

**① 严格定义**：Dispatcher 执行工具前后的三道闸——执行前**路径规范化+项目根白名单**（防 path traversal）、执行中 `asyncio.wait_for` 分级超时（读 10s/写 30s/headless 120s）、执行后**输出截断**（保头保尾+中间省略标记）。

**② 大白话**：**车间安全规程**。带电作业限时（超时：工具挂死不能连累整个循环）；碎屑要清扫（截断：10MB 日志塞进上下文=把老板的桌子埋了）；危险区拉警戒线（路径防护：模型"好心"读 `.git/config` 或 `../../.ssh/id_rsa` 都是攻击面——提示注入可以让模型产生恶意路径）。

**③ 举例**（可直接抄进 sandbox.py 的两段核心）：

```python
def resolve_in_root(root: Path, rel: str) -> Path:
    p = (root / rel).resolve()
    if not p.is_relative_to(root.resolve()):
        raise PathEscapeError(f"{rel} escapes project root")
    if any(part in DENY_PARTS for part in p.parts):   # {".git", ".env", "__pycache__"}
        raise DeniedPathError(str(p))
    return p

def truncate(text: str, head=1500, tail=300) -> str:
    if len(text) <= head + tail + 50:
        return text
    return f"{text[:head]}\n...[中间省略 {len(text)-head-tail} 字符]...\n{text[-tail:]}"
```

为什么截断要**保头保尾**：错误信息常在尾部（traceback），只保头会丢关键——"中间省略"是 token 预算和信息量的最优折中。

**④ 演进**：裸 await（工具卡死全卡死）→ wait_for 超时 → 输出截断 → 路径防护 → （生产级进阶：进程隔离/容器沙箱/权限系统 M09）。本模块做前四层。

**⑤ 易错点**：
- Windows 路径大小写不敏感+反斜杠：`resolve()` 前统一 posix 化，否则 `is_relative_to` 判定漂移
- `wait_for` 取消后子进程可能残留（M06 headless）：要 `Process.kill()` 显式清理
- 防护失败要返回 ToolResponse 而非抛异常——被拦的路径攻击也是一次"正常失败"

### 1.5 乐观锁文件编辑（并发写防护）

**① 严格定义**：悲观锁=先锁再改（锁期间他人等待）；**乐观锁**=不锁，提交时校验"我读之后没人改过"（版本号 content hash），冲突则失败提示重读。Agent 文件编辑必须乐观：冲突方是"用户在编辑器手动改文件"，锁不住人；模型从读到写隔着一轮推理（几十秒），悲观锁会把所有人饿死。

**② 大白话**：**共享文档的交接班制度**。你抄录图纸时记下版本号（hash），改完交回时管理员核对：图纸还是你抄录时的版本吗？是→你的修改生效；不是（有人先改了）→**拒绝合并，重新抄最新版再改**。关键决策：冲突后**不自动合并**——让模型重读重写；自动合并产生的"缝合怪"（你的改动+别人的改动物理拼接）比冲突本身更难调试。

**③ 举例**：完整冲突流（可直接参考手写）：

```python
async def write_file(self, path: str, content: str, expect_hash: str) -> ToolResponse:
    p = resolve_in_root(self.root, path)
    cur = sha16(p.read_text(encoding="utf8")) if p.exists() else EMPTY
    if cur != expect_hash:
        return ToolResponse(ok=False, error=ToolError(
            kind=ErrorKind.CONFLICT, tool="write_file",
            message=f"版本冲突: 期望 {expect_hash[:8]} 实际 {cur[:8]}（文件已被外部修改）",
            hint="先重新 read_file 获取最新版本，再基于新内容重新修改"))
    backup = self.checkpoint.snapshot(p)          # M06 检查点：写前快照
    p.write_text(content, encoding="utf8")
    return ToolResponse(ok=True, summary=f"已写入 {path} ({len(content)}B)",
                        artifacts=[Artifact(type="diff", ref=str(backup))])
```

**④ 演进**：无保护（后写覆盖，静默丢改动）→ mtime 检查（精度坑：同秒两次修改检测不到）→ **content hash（SHA-256 前 16 位）**（本项目）→ git 原子提交/CRDT（重武器，个人项目过度设计）。

**⑤ 易错点**：
- hash 覆盖"内容"，mtime 只做辅助信号
- 快照要在写**之前**做（顺序错了没有回头路），快照失败要阻断写入
- read 必须返回 (content, hash) 二元组——模型下一轮 write 时要带上这个 hash

## 2. 接口设计（完整签名 = 你要手写的契约）

```python
# tools/registry.py
@dataclass
class ToolMeta:
    """工具身份证：Dispatcher 分流、M09 权限分级、M13/M15 过滤全靠它。"""
    name: str; description: str
    readonly: bool                    # Dispatcher 读写分流依据
    risk: Literal["low", "medium", "high"]   # M09 权限分级依据
    tags: set[str] = set()            # 模式/子代理过滤依据

class ToolRegistry:
    def register(self, tool: "BaseTool") -> None: ...
    def tool_specs(self) -> list[dict]: ...          # FC 声明（给模型）
    def get(self, name: str) -> "BaseTool": ...
    def filter(self, *, tags=None, readonly=None) -> "ToolRegistry": ...  # 视图裁剪
    def namespaced(self, ns: str) -> "ToolRegistry": ...  # mcp__godot__ 前缀

class BaseTool(ABC):
    meta: ToolMeta
    Params: type[BaseModel]                       # pydantic 参数模型
    @abstractmethod
    async def run(self, **params) -> ToolResponse: ...

def register_tool(**meta_kwargs) -> Callable[[type[BaseTool]], type[BaseTool]]: ...

# tools/response.py
class ErrorKind(Enum):
    NOT_FOUND="not_found"; VALIDATION="validation"; TIMEOUT="timeout"
    CONFLICT="conflict"; DENIED="denied"; INTERNAL="internal"

@dataclass
class ToolError: kind: ErrorKind; tool: str; message: str; hint: str | None
@dataclass
class Artifact: type: Literal["diff","file","image","log"]; ref: str; meta: dict | None

# tools/sandbox.py
def resolve_in_root(root: Path, rel: str) -> Path: ...
def truncate(text: str, head: int = 1500, tail: int = 300) -> str: ...
async def run_with_timeout(coro, seconds: float, on_cancel: Callable | None) -> Any: ...

# tools/file_lock.py
def sha16(text: str) -> str: ...
class OptimisticFileStore:
    async def read(self, path: str) -> tuple[str, str]: ...          # (content, hash)
    async def write(self, path: str, content: str, expect_hash: str) -> ToolResponse: ...
```

## 3. 关键难点参考片段：schema 清洗

pydantic 生成的 schema 含 `title`、`$defs` 等 FC API 不接受/不一致的字段，注册时必须清洗（90% 手写教程漏掉，跑到真 API 才炸）：

```python
def to_fc_schema(params: type[BaseModel]) -> dict:
    schema = params.model_json_schema()
    def clean(node: dict) -> dict:
        node.pop("title", None)
        if "$defs" in schema:                      # 内联 $ref（嵌套模型）
            node.pop("$defs", None)
            defs = schema["$defs"]
            def deref(n):
                if "$ref" in n:
                    return deref(defs[n["$ref"].split("/")[-1]])
                for k, v in list(n.items()):
                    if isinstance(v, dict): n[k] = deref(v)
                    if isinstance(v, list): n[k] = [deref(x) if isinstance(x, dict) else x for x in v]
                return {a: b for a, b in n.items() if a != "title"}
            return deref(node)
        return node
    return clean(schema)
```

## 7. 面试拷打（附详细参考答案）

**1. Function Calling 里"模型执行了函数"这句话对吗？执行责任在谁？**
答：错。模型只输出**结构化建议**（tool_calls：工具名+JSON 参数），执行发生在客户端——超时控制、沙箱防护、错误处理、重试全是客户端责任。这个设计是刻意的安全边界：模型（不可信的文本生成器）永远摸不到真实系统，开发者保留全部执行权。类比：模型是开处方的医生，抓药的是你——处方笺上写的剂量错了，责任在你抓药前不核对。

**2. tools 参数里的 description 你会写什么？它影响什么指标？**
答：写"**何时该用/何时不该用**"的场景说明（"读取项目内文本文件。修改任何文件前必须先调用它获取当前内容与版本 hash"），不写实现细节。它影响：工具选择准确率（模型靠 description 区分相似工具）、参数填写正确率（Field 的 description 是填参指南）、误用率（写清"何时不该用"能挡住误选）。本质：description 是写给模型看的提示词——提示工程的延续。

**3. arguments 为什么是字符串？流式下怎么聚合？**
答：协议设计上 arguments 是 JSON **字符串**（模型逐 token 生成，token 边界不保证对齐 JSON 结构边界），必须 json.loads 后使用。流式下分片到达：id/name 在首帧、arguments 按块拼接——StreamAggregator（M02）按 index 分桶、args 缓冲追加、finish_reason 时整体 loads 验证。不聚合就解析必失败（半个 JSON）。

**4. 工具异常为什么回传而不上抛？"错误也是数据"在哪些地方还会用到？**
答：回传让模型读到错误自己纠正（ReAct 的 Observation 纠错精髓——路径错了换路径、参数错了改参数）；上抛则中断循环，模型失去自愈机会。"错误也是数据"的同源场景：M02 的错误分类树（Retryable 与否是数据不是异常语义）、M06 的 headless 校验错误回填驱动自修复（Reflection 雏形）、M09 的权限拒绝也返回 ToolResponse 而非炸循环。唯一例外：系统性失败（熔断打开/鉴权失效）该中断就中断。

**5. 乐观锁 vs 悲观锁，Agent 文件编辑为什么必须乐观？版本号用 mtime 还是 hash？**
答：悲观锁适合短临界区（毫秒级持锁）；Agent 的"读→想→写"隔着一轮推理（几十秒），悲观锁会把用户饿死；且冲突方是"用户在编辑器手动改文件"——锁不住人。乐观锁把并发变成"一次可自愈的失败"：hash 不匹配 → 模型重读重改。版本号用 content hash（SHA-256 前 16 位）不用 mtime：mtime 同秒两次修改检测不到（精度坑），且文件被 touch（内容没变）会误报冲突；hash 直接对内容负责。

**6. 冲突后为什么不自动三方合并？**
答：三方合并需要 base/ours/theirs 三方语义对齐，而模型的修改是**语义级**的（重写了一个函数），用户的手改也是语义级的——文本级三方合并会产生语法正确但语义缝合怪的代码（两个都对，拼起来错），比冲突本身更难调试。让模型重读最新版再改：模型拿到最新上下文重新推理，产出语义自洽的结果。原则：**冲突是便宜的（一次重读），缝合怪是昂贵的（人工调试）**。

**7. 沙箱三层防护分别防什么攻击？**
答：①路径防护防 path traversal 与敏感文件读取——提示注入可诱导模型读 `.git/config`（窃取仓库信息）或 `../../.ssh/id_rsa`（窃取密钥），`resolve()+is_relative_to+denylist` 三连拦；②超时防资源耗尽——工具挂死（headless 游戏主循环不退出、死循环脚本）会占死事件循环，wait_for 强制打断并清理子进程；③截断防上下文撑爆——10MB 日志全量回填=烧掉整个上下文预算（M07 的账直接爆），保头保尾既留错误信息又控预算。

**8. 30 个工具全量发给模型有什么问题？怎么解决？**
答：问题：选择准确率下降（相似工具混淆——read_file vs search_files vs list_symbols），token 开销大（每个 spec 都占上下文），幻觉工具调用上升。方案四连：①M13 模式过滤（ask 物理上只给只读工具）；②M15 子代理工具白名单（每个子代理 3~5 个相关工具）；③命名空间隔离（mcp__godot__ 前缀防重名）；④tool retrieval（工具太多时按任务检索相关工具子集——把 RAG 思想用在工具上）。

**9. summary 与 artifacts 为什么要分离？**
答：消费者不同：模型要的是"人话结论"（summary：写入成功，35 行，diff 见 #12）——省 token 且足够决策；前端要的是"结构化渲染物"（artifacts：diff 引用、文件路径、截图 URL）——渲染 Diff 审查卡片、可点击跳转。混在一起的代价：要么模型被迫读 diff 全文（token 浪费），要么前端拿不到结构化数据（只能正则解析文本）。一个调用喂饱两个消费者=接口设计的多消费者意识。

**10. 开放题：设计一个"运行用户提交 GDScript"的工具，安全清单列十条。**
答：①进程隔离——独立子进程运行，绝不 import 进主进程；②超时硬杀——wait_for + --quit-after + Process.kill 兜底（防死循环）；③文件系统白名单——只可访问项目 tmp 目录（resolve_in_root）；④资源限制——子进程级内存/CPU 限额（Windows Job Object / cgroup）；⑤输出截断——stdout/stderr 截断防上下文爆；⑥网络禁用——沙箱内无网络（防恶意脚本外传数据）；⑦敏感环境隔离——清空 env（API key 不进子进程）；⑧权限分级——risk=high，M09 必须用户确认才执行；⑨审计落库——谁在哪个会话执行了什么代码，M19 审计表留痕；⑩检查点前置——运行前快照可能被改的文件，出事可回滚（M06）。核心思想：默认一切输入不可信，纵深防御。
