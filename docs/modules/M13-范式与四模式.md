## 0. 本模块在项目中的位置

M03 的 Loop 是"单步推理-行动循环"；本模块在它之上加**任务级策略**——同一个循环，不同"驾驶模式"：

```text
ask   单轮问答，检索增强，不动文件          —— M12 已联通，本模块正式化
craft 执行+自检：改代码→headless 验→不过则修  —— Reflection 内嵌领域回路
plan  先出 DAG 计划，人批了再逐步执行，可 re-plan —— Plan-and-Solve
multi 拆子任务并行派发 Subagent             —— M15 完成编排器后合体
```

**交付后状态**：`/plan 重构战斗系统为组件化架构`——先出任务 DAG（每步含验收标准）→ 用户批准/修改 → 逐步执行（每步 craft 闭环）→ 步骤失败触发 re-plan。

## 1. 知识点详解

### 1.1 Plan-and-Solve：先规划后执行

**① 原理**

一步到位做复杂任务 = 把"规划"和"执行"挤在一个上下文里互相干扰（模型边想边做，做着做着忘了目标）。Plan-and-Solve 显式拆两阶段：

```text
Phase 1 规划：输入任务+项目现状 → 输出步骤 DAG
  每步: {id, goal, files_likely, accept_criteria, depends_on[]}
Phase 2 执行：按拓扑序逐步跑 craft 闭环（M06 的读-改-验），
  步骤产物（文件/结论）写入"任务状态板"，后续步骤可引用
Re-plan：某步失败且重试耗尽 → 携失败上下文回到 Phase 1 修订剩余 DAG（已完成步骤不重做）
```

**为什么 DAG 而非线性列表**：步骤间有依赖（"改场景"依赖"写脚本"）但非全序——DAG 表达并行机会（multi 模式用），线性列表表达不了"步骤 2 和 3 可以同时做"。

**验收标准（accept_criteria）是 plan 模式的灵魂**：没有它，"执行完"无法判定，re-plan 无据可依。每步的 criteria 要可机器验证（"headless check 通过"、"测试 3/3 绿"）优先于"代码看起来合理"这种人话。

**② 演进**：CoT（隐式规划混在生成里）→ Plan-and-Solve（2023 论文，把 "Let's first understand the problem and devise a plan" 显式化）→ ReWOO（Reason Without Observation：规划时预算全部工具调用，执行阶段不再看结果调整——省 token 但刚性）→ LLM+P（PDDL 经典规划器做执行）。Agent 工程线：Claude Code 的 plan mode（人工审批关口）= 本项目形态。

**③ 最小案例**：DAG 数据结构与拓扑执行

```python
@dataclass
class PlanStep:
    id: str; goal: str
    accept_criteria: str                  # 尽量可机器验证
    depends_on: list[str] = field(default_factory=list)
    status: Literal["pending","running","done","failed","skipped"] = "pending"

def topo_order(steps: list[PlanStep]) -> list[PlanStep]:
    """Kahn 算法：入度表 → 零入度出队 → 邻接减度。检测环：出队数 < 总数即有环。"""
    indeg = {s.id: len(s.depends_on) for s in steps}
    by_id = {s.id: s for s in steps}
    queue = [s for s in steps if indeg[s.id] == 0]
    order = []
    while queue:
        s = queue.pop(0); order.append(s)
        for t in steps:
            if s.id in t.depends_on:
                indeg[t.id] -= 1
                if indeg[t.id] == 0:
                    queue.append(by_id[t.id])
    if len(order) != len(steps):
        raise CyclicPlanError("计划存在循环依赖")     # 模型偶尔产出环，必须拦
    return order
```

**④ 易错点**
- 模型产出的 DAG 可能含环/幽灵依赖（depends_on 引用不存在的 id）——解析后必须校验（上面两行防御）
- 计划步骤太粗（"完成战斗系统"=没计划）或太细（50 步改一次的微操）——提示里给粒度锚点（3~10 步，每步 1~3 文件）
- 执行中每步都要把"任务状态板"注入上下文——模型不知道前面步骤做了什么会重复劳动

### 1.2 Reflection / Reflexion：自我修正回路

**① 原理**

生成 → **批判**（评估这次输出）→ 修正 → 循环，直到批判通过或预算耗尽。两种嵌入方式：

```text
内回路（craft 模式，本节核心）：执行后跑客观验证器（headless/测试/Diff 审查），
  验证反馈作为 Reflection 输入——验证器是"外部批评者"，比模型自评可靠得多
外回路（Reflexion 完整版）：任务失败后生成"语言化反思"存入记忆，
  下次尝试时注入——"上次我在这里因为 X 失败，这次先 Y"
```

**核心洞见：批评者的可靠性决定 Reflection 上限**。让模型"自我感觉良好式复评"几乎无增益（它倾向给自己打高分）；接客观信号（编译错误、测试红、运行崩溃——M06 的 headless 闭环）才是真 Reflection。这也是 M06 埋的"校验错误回填驱动自修复"的正式化。

**② 演进**：Basic Prompting（一次生成）→ Self-Refine（2023：模型自评自改，纯内省，增益不稳）→ Reflexion（2023：语言化反思+记忆跨尝试）→ 客观验证器回路（RLHF 时代的 verifier 思想——也是 M18 GRPO 可验证奖励的前身）。记住链路：**自省式反思 < 记忆式反思 < 客观验证式反思**。

**③ 最小案例**：craft 的自检回路

```python
async def run_with_reflection(self, session, edit_task, max_fixes=3):
    result = await self.loop.run(session, edit_task)          # 第一轮：改代码
    for i in range(max_fixes):
        check = await self.godot.check_and_test()             # 客观验证器
        if check.ok:
            return result
        reflect_input = f"""你刚完成的修改未通过验证：
{check.errors}
请分析失败原因（语法/逻辑/资源引用？），修复后重试。这是第 {i+1} 次修正。"""
        result = await self.loop.run(session, reflect_input)  # 反馈驱动修正
    return await self._escalate(session, result)              # 升级：交人工/降级任务
```

**④ 易错点**
- `max_fixes` 必须有限：同一个错修三遍还不过，继续修大概率是死循环（配合 M03 LoopDetector 双保险）
- 反思上下文要**带上前几轮的失败摘要**——否则模型修好 A 又引入 B，来回打地鼠
- 修不动时的升级策略（问用户/缩小任务范围）比硬重试有价值——"知难而退"是工程能力

### 1.3 四模式状态机与统一装配

**① 原理**

四模式不是四个独立系统，是**同一个 Loop 的四种配置**（策略对象模式）：

```python
@dataclass
class ModeProfile:
    """每个模式 = 一组差异配置，其余全复用 M03 底座"""
    system_extra: str                    # 模式专属系统提示
    tools_filter: set[str] | None        # 工具白名单（ask 不给写工具！）
    reflection: ReflectionConfig | None  # 自检回路配置
    plan_gate: bool = False              # 是否需要人工批准计划
    budget: BudgetConfig                 # 模式级预算默认值

PROFILES = {
  "ask":   ModeProfile(system_extra=ASK_PROMPT, tools_filter=READONLY_TOOLS,
                       budget=Budget(max_steps=8, usd=0.1)),
  "craft": ModeProfile(system_extra=CRAFT_PROMPT, reflection=ReflectionConfig(max_fixes=3),
                       budget=Budget(max_steps=25, usd=0.5)),
  "plan":  ModeProfile(system_extra=PLAN_PROMPT, plan_gate=True,
                       budget=Budget(max_steps=40, usd=1.5)),
  "multi": ModeProfile(system_extra=MULTI_PROMPT, budget=Budget(max_steps=60, usd=3.0)),
}
```

模式切换：用户 `/plan` 命令（M14）、M12 路由（code_edit→craft）或 Agent 自荐（ask 中发现"这需要改代码"→ 建议切换，**不擅自切**——模式切换是用户可感知的重大状态变化）。

`ask 不给写工具` 是重要设计：工具集即能力边界，模式控制的最彻底形式是"物理上不可为"——比提示词里说"不要改文件"可靠一个量级（M04 的 registry.filter 在此兑现）。

**② 演进**：范式各自为战（一个范式一个 Agent 类，hello-agents 形态）→ 范式=可插拔策略（模式配置化，DSH/Claude Code 形态）。前者利于教学对应论文，后者利于生产演进——本项目 M13 从前者重构为后者，**这次重构本身就是面试素材**（"什么时候该把类继承改成组合配置"）。

**③ 最小案例**：模式入口的装配

```python
class AgentEngine:
    async def run(self, session, input, mode: str) -> LoopResult:
        profile = PROFILES[mode]
        tools = self.registry.filter(names=profile.tools_filter) if profile.tools_filter \
                else self.registry
        loop = AgentLoop(self.llm, Dispatcher(tools, ...),
                         ContextBuilder(..., system_extra=profile.system_extra),
                         BudgetTracker(profile.budget), self.bus)
        if mode == "plan":
            return await self.plan_flow(loop, session, input, profile)
        if mode == "craft":
            return await self.craft_flow(loop, session, input, profile)
        return await loop.run(session, input)          # ask/multi 走标准流
```

**④ 易错点**
- 模式间切换要重置预算与 LoopDetector，但**保留上下文**（plan 批准后进 craft，用户意图链不能断）
- plan_gate 的人工批准复用 M09 确认门（PendingConfirm 挂整个 DAG 渲染）——不要另造轮子
- multi 模式本 Sprint 只出骨架（orchestrator 在 M15），发布说明里标注实验特性

### 1.4 Plan 的表示与渲染（用户审批界面）

**① 原理**：计划要给人看——渲染为编号清单+依赖缩进+每步验收标准；审批界面支持三种动作：**批准全案 / 编辑步骤（增删改序）/ 拒绝并说明**（拒绝理由回填，模型重新规划）。CLI 用缩进文本，Web（M20）用可拖拽卡片。

**②③ 合并**：渲染器 30 行（topo_order 结果缩进化）；易错：用户编辑后的 DAG 必须重新过环检测——用户也可能造出环。

## 2. 接口设计（完整签名）

```python
# agent/paradigms/base.py
@dataclass
class ModeProfile: ...                      # 见 1.3
class ModeFlow(ABC):
    mode: ClassVar[str]
    @abstractmethod
    async def execute(self, engine: "AgentEngine", session: Session,
                      input: str, profile: ModeProfile) -> LoopResult: ...

# agent/paradigms/ask_mode.py / craft_mode.py
class AskFlow(ModeFlow): ...
class CraftFlow(ModeFlow):
    def __init__(self, godot: GodotRunner): ...
    async def execute(...) -> LoopResult: ...          # run_with_reflection

# agent/paradigms/plan_mode.py
@dataclass
class Plan: steps: list[PlanStep]; rationale: str
    def topo(self) -> list[PlanStep]: ...
    def render(self) -> str: ...                       # 审批视图
class PlanFlow(ModeFlow):
    async def _generate_plan(self, session, input) -> Plan: ...
    async def _gate(self, session, plan: Plan) -> Plan: ...    # M09 确认门
    async def _execute_steps(self, session, plan: Plan) -> None: ...
    async def _replan(self, session, plan, failed_step, error) -> Plan: ...

# agent/paradigms/multi_mode.py（Sprint 10 与 M15 合体前为骨架）
class MultiFlow(ModeFlow): ...
```

## 3. 关键难点参考片段：re-plan 的"已完成保护"

失败重新规划时，最大风险是新计划把已完成步骤**换个说法重做**（甚至回滚已有成果）。三道保护：

```python
async def _replan(self, session, plan, failed, error):
    done = [s for s in plan.steps if s.status == "done"]
    replan_prompt = f"""原目标：{session.task_goal}
已完成（这些不许重做，成果已在文件系统里）：
{chr(10).join(f'- {s.id}: {s.goal} (验收: {s.accept_criteria} 已通过)' for s in done)}
失败步骤：{failed.id} {failed.goal}
失败详情：{error}
请只重新规划【失败步骤及其下游】，输出新的剩余 DAG。保持已完成文件的现状。"""
    new_plan = await self._generate_plan_with(replan_prompt)
    return merge_steps(done=done, remaining=new_plan)   # 合并时校验依赖闭合
```

为什么难：合并要保证新 DAG 对 done 步骤的引用合法（新步骤 depends_on 已完成项），且 merge 后再跑一次环检测——三处校验缺一不可。
