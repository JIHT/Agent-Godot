## 0. 本模块在项目中的位置

**大白话**：M03 造好了发动机（ReAct 循环），本模块给车装**换挡器**。同一台发动机，四种驾驶模式：**ask**（顾问——只答不改）、**craft**（执行者——自主干到底）、**plan**（架构师——先出图纸人批准再动手）、**multi**（车队——拆任务派车队并行干）。

这正是 Cursor/CodeBuddy 顶部那个模式切换器的内核。**模式不是四套代码，而是同一循环挂不同配置**（策略对象）。

### ★ 核心认知：模式层 ⊥ 范式层（两层正交，不可绑定）

这是本模块最容易被写错的地方。先把关系钉死：

```
┌──────────────────────────────────────────────┐
│  模式层（产品概念 · 人机协作契约）              │
│  Ask / Craft / Plan / Multi                   │
│                                               │
│  回答：模型能做什么？做之前要不要问人？          │
│  维度：工具权限 · 审批门 · 自主度 · 编排形态    │
└──────────────────────────────────────────────┘
                    ⊥ 正交
┌──────────────────────────────────────────────┐
│  范式层（技术手段 · 执行机制）                  │
│  ReAct / Reflection / Plan-and-Solve /        │
│  Multi-Agent                                  │
│                                               │
│  回答：循环怎么组织？怎么纠错？怎么规划？        │
│  特点：按需组合启用，由实际问题与操作决定        │
└──────────────────────────────────────────────┘
```

**模式划定"能力边界"，范式决定"边界内怎么运作"。二者不是一一对应关系。**

业界口径完全支持这个分层。CodeBuddy 官方对用户解释三模式时说的是：

> **"'Craft' 是核心的智能体模式，而 'Ask' 和 'Plan' 更像是用户在使用 'Craft' 或普通对话时采取的两种不同提问策略。"**

翻译成工程语言就是：**Craft 是完整引擎，Ask/Plan 是在它之上加的约束档位**。档位限制的是"边界"，不是"引擎内部的运作方式"——ask 模式里模型照样在跑 ReAct 多轮检索，craft 模式里模型照样会自主拆解子任务。

### 四模式与业界对齐

| 本项目 | CodeBuddy 对齐 | Cursor 参考 |
|---|---|---|
| `ask` | **Ask**（顾问：单次问答） | Ask（只读代码库搜索） |
| `craft` | **Craft**（执行者：全自动智能体协作） | Agent（自主多文件修改 + 跑命令） |
| `plan` | **Plan**（架构师：先出分步计划人确认） | Plan（出可审阅计划，研究但不写） |
| `multi` | —（CodeBuddy 无此模式） | **Agents Window（3.0+）/ `/multitask`（3.2）** |

关于 `multi` 的说明：Cursor **没有** Multi 模式，它的多 agent 并行能力藏在 Agents Window 里——"每个 agent tab 可持有自己的 mode、model、worktree；3.2 的 `/multitask` 让异步子代理并行而非排队"。

本项目把它**产品化提到模式切换器上**，做成一个显式模式。这是比 Cursor 更激进的一步：用户一眼能看见"我现在是单干还是派车队"，代价是模式切换器多一个档位。设计上 `multi` = 能力边界（`per_worker`）+ 编排形态（并行），内部仍按需组合 ReAct / Reflection / Plan-and-Solve。

**交付后状态**：`godot-agent plan "给游戏加存档系统"` → 出 DAG 请你审批 → 批准后逐步执行、失败节点 re-plan；craft 模式改代码自动 headless 校验不过不交卷。

## 1. 知识点详解（每节五段：定义 → 大白话 → 举例 → 演进 → 易错点）

### 1.1 模式层：四模式 = 人机协作契约

**① 严格定义**：模式（Mode）= **产品层概念**，定义一份"人机协作契约"，由四个正交维度刻画：

| 维度 | 含义 | 取值 |
|---|---|---|
| **工具权限** | 模型能碰哪些工具（物理能力边界） | `readonly` / `all` / `per_worker` / 白名单 |
| **审批门** | 动作前要不要人签字 | 无 / 操作级（M09 确认门）/ 任务级（DAG 审批） |
| **自主度** | 谁驱动循环、模型能走多远 | 多轮检索自主 / 全自主到底 |
| **编排形态** | 单干还是派车队 | 单代理 / 多代理并行 |

四模式就是这四维的四组预设值：

| 模式 | 定位（CodeBuddy 口径） | 工具权限 | 审批门 | 自主度 | 编排形态 |
|---|---|---|---|---|---|
| `ask` | 顾问：只答不改 | `readonly` | 无 | 中（多轮检索自主） | 单代理 |
| `craft` | 执行者：自主干到底 | `all` | 操作级（写确认门） | 高 | 单代理 |
| `plan` | 架构师：先出图纸人批准 | `all`（**规划期只研究不写**） | 任务级（DAG 审批） | 中（执行期自主） | 单代理 |
| `multi` | 车队：拆任务并行派发 | `per_worker` | 任务级 + 聚合确认 | 高 | **多代理并行** |

注意 `plan` 的工具权限：**Cursor 的 Plan 模式也是全工具**——"Creates detailed implementation plans, asks clarifying questions / All tools enabled"，它能读能搜，只是**不写代码**。本项目同理：`plan` 持有全工具用于规划期研究代码库，批准后的执行阶段**委托给 craft 子循环**（见 §1.3 代码铁证）。

**② 大白话**：**换挡器不是换发动机**。运动模式（craft 低温度+验证回路）、经济模式（ask 只读巡航）、autopilot（plan 先出图纸）、车队调度（multi 并行派发）——发动机（M03 循环）从没换过，换的是油门响应（采样参数）、限速器（工具白名单）、导航仪（计划图）。

**模式是"驾照等级"，不是"驾驶车型"**：C1 能开小车、A1 能开摩托——等级限制的是"你能碰什么"，不是"你只能用一种技术开"。

**③ 举例**：四模式配置矩阵（可直抄进代码做默认值）：

```python
DEFAULT_MODES = {
 "ask":   ModeConfig(tools="readonly",  temperature=0.7, verify=None,  plan_first=False),
 "craft": ModeConfig(tools="all",       temperature=0.1, verify="L1+",  plan_first=False),
 "plan":  ModeConfig(tools="all",       temperature=0.2, verify="L1+",  plan_first=True),
 "multi": ModeConfig(tools="per_worker",temperature=0.3, verify="per_task", plan_first=True),
}
```

**④ 演进**：硬编码 `if mode ==`（每处散落）→ 配置文件 → **策略对象+注册表**（本项目）。趋势：模式进一步产品化（自定义模式=用户可写 yaml 定义自己的 ModeConfig，M19 设置页提供）。

业界侧：CodeBuddy 三模式（Craft 为引擎，Ask/Plan 为档位）→ Cursor 四模式（新增 Debug，3.0 引入 Agents Window 多 agent 并行）→ 本项目四模式（把 Multi 从"窗口能力"提升为"显式模式"）。

**⑤ 易错点**：
- **最易错：把模式名当范式名用**。"craft 模式 = Reflection"、"ask 模式 = ReAct" 都是错的（§1.3 用代码证明）。模式是契约，范式是机制。
- **模式切换是"改契约"不是"换算法"**——切到 ask 之后模型照样在跑 ReAct 多轮检索，只是手上没了写工具。
- 模式切换在**会话内**生效但工具视图要重建（`registry.filter` 是视图不是拷贝）。
- `craft` 的 `temperature=0.1` 与 M02 路由表是同一处配置的两个入口——单一事实源（`models.yaml`），别在两处写死。
- `plan` 模式被拒绝审批后要**干净退出**（不残留半执行状态），确认门复用 M09。

### 1.2 范式层：按需组合的执行机制

**① 严格定义**：范式（Paradigm）= **技术手段层**，回答"循环怎么组织、怎么纠错、怎么规划"。四个经典范式在本项目都是**可插拔的执行机制**，**由实际问题与操作决定是否启用，不与模式绑定**。

| 范式 | 回答的问题 | 本项目落点 |
|---|---|---|
| **ReAct**（Yao 2022） | 每步怎么做决策？ | M03 主循环——**四模式共用底座，强制启用** |
| **Reflection**（Reflexion, Shinn 2023） | 做错了怎么发现并修正？ | M06 headless 客观验证器 + `on_tool_done` 钩子 |
| **Plan-and-Solve**（Wang 2023） | 长任务怎么不跑偏？ | 结构化 DAG + 人审批 + re-plan（显式）/ 模型自主拆解（隐式） |
| **Multi-Agent**（Orchestrator-Worker） | 大任务怎么加速？ | M15 Orchestrator + A2A |

其中 Reflection 三形态按可靠性排序：**自评**（模型给自己打分——倾向高分，弱）/ **互评**（另一模型评——好些）/ **客观验证器**（外部工具可判定对错——最强，**本项目采用**）。

关键认知：**范式是"能力"不是"档位"**。模式划定边界，边界内模型按实际需要自由组合范式。这才 CodeBuddy"Craft 是引擎、Ask/Plan 是档位"的技术含义——引擎内部该用哪种技术，取决于**当前这一步在做什么**，不取决于外壳叫什么名字。

**② 大白话**：**模式是驾照等级，范式是驾驶技术**。有 C1 驾照不代表只会一种技术；开摩托照样要"看后视镜、倒车入库、预判路况"。

- **ReAct** = 边开边看（每步看一眼路况再决定方向盘）
- **Reflection** = 倒完车下来看一眼停正了没（客观仪器测量，不是"我觉得停得挺好"）
- **Plan-and-Solve** = 出发前先规划路线（哪段高速、哪段辅路、哪些可以并行）
- **Multi-Agent** = 几辆车分头送几批货

**③ 举例**：Reflection 在本项目的实现——客观验证回路，挂在 `on_tool_done` 钩子上：

```python
class VerifyLoop:
    WRITE_TOOLS = {"write_file", "godot_write_script", "godot_edit_scene"}
    def __init__(self, runner: GodotRunner, max_fixes: int = 3): ...

    async def after_write(self, tool: str, response: ToolResponse,
                          session: Session) -> str | None:
        """返回"未通过的错误摘要"或 None（通过）。Loop 把它注入下一轮。"""
        if tool not in self.WRITE_TOOLS or not response.ok:
            return None                                  # 只验成功的写
        result = await self.runner.check()               # L1 起步，配置到 L3
        if result.ok:
            return None
        self.fixes += 1
        if self.fixes > self.max_fixes:
            return ("验证连续失败超限，请向用户确认：继续修复或 /rewind 回滚。"
                    f"最后一次错误：\n{result.errors[:1500]}")
        return (f"⚠️ 写入后 headless 校验未通过（第{self.fixes}次），请修复后重写：\n"
                f"{result.errors[:1500]}")
```

**④ 演进**：

- **ReAct**：直接 prompting（一次性回答，错就是错）→ CoT（2022，教模型"想清楚"）→ ToT（2023，推理树）→ **ReAct**（2022.10，教模型"边想边做边看结果"）→ Function Calling 原生化（2023.6）→ Agent Loop 工程（本项目）
- **Reflection**：无验证（改完就交）→ 自评 Reflection（弱）→ Reflexion（语言化反思+记忆，选读）→ **工具增强自修正**（2023 主流：验证器是工具，本项目采用）→ M18 GRPO 可验证奖励（同一思想训练化）
- **Plan-and-Solve**：CoT 一步到位 → ReAct（边走边看，长任务漂移）→ Plan-and-Solve（2023）→ ReWOO（计划与执行解耦）→ LLM+PDDL（形式化规划器，选读）

**⑤ 易错点**：
- **头号易错：把范式与模式 1:1 绑定**。本项目早期文档就犯过这个错（写成"ReAct→ask / Reflection→craft / Plan-and-Solve→plan / Multi-Agent→multi"）。看 §1.3 的代码铁证就知道这是错的。
- Reflection 的验证器**不是"再问一遍模型"**——模型自评像让学生给自己批卷（基本都打 90 分），客观仪器不说谎。
- **范式启用的判据是"实际问题"，不是"模式名"**。同一个 craft 模式里，改一行注释不需要 Reflection，改核心模块必须 Reflection——这由模型根据实际风险判断，不由模式名写死。
- 验证成本也是钱：L1 秒级每次写都验、L3 分钟级只在关键节点验——分级配置。
- `max_fixes` 触顶后**必须**升级给人（确认门），静默放弃=半成品交卷。
- 验证错误回填要走 M03 的 Observation 通道（错误也是数据），别抛异常炸循环。

#### 分级校验：M06 原子四级 ↔ `ModeConfig.verify` 累积档

两套命名并存，是最容易读错的地方，这里对齐一次。

**M06 定义的原子四级**（`tools/godot/headless.py`，每级一个独立方法）：

| 原子级 | 命令 | 拦什么 | 超时 |
|---|---|---|---|
| **L1 语法** | `--check-only` | GDScript 解析错（缩进 / 未定义变量 / 签名不匹配） | 15s |
| **L2 导入** | `--import` | 资源引用断链、场景格式错 | 120s |
| **L3 测试** | `-s tests/run.gd` | 逻辑回归（测试套件红） | 120s |
| **L4 运行** | 跑 N 帧 + stdout 断言 | 运行时崩溃（空引用 / 死循环 / 信号连接错） | 120s |

**`ModeConfig.verify` 用的是累积档**（"跑到哪一级"），不是"只跑哪一级"：

| verify | 实际执行序列 | 适用 |
|---|---|---|
| `None` | 不校验 | `ask` |
| `"L1"` | L1 | 高频写、要秒级反馈 |
| `"L1+"` | L1 → L2 | **`craft` / `plan` 默认** |
| `"L3"` | L1 → L2 → L3 | 关键节点、发布前 |
| `"per_task"` | 此处不跑，由 plan/multi 节点边界显式触发（M15） | `multi` |

三条约束：

1. **顺序固定 L1 → L2 → L3**。L2 必须早于引用它的校验——Godot 资源系统要先构建导入缓存（`.godot` 目录）才能被 check 引用，**新建的贴图/场景没导入过，缓存里没有**，后续校验会集体报"资源不存在"的**假错**（M06 §7.6）。
2. **L4 不在 `verify` 取值内**。它有副作用（截图 / 改游戏状态）且需用户确认，只能由用户显式调用 `runner.run_scene()`。
3. **鸭子类型降级**。runner 未实现某级方法（如单测里只有 `check()` 的 `FakeRunner`）→ 跳过该级继续下一级，不报错。这一条让同一份 `VerifyLoop` 既能跑四级齐全的真实 `GodotRunner`，也能跑极简假 runner——**向后兼容的关键**。

### 1.3 ★ 范式 × 模式矩阵（本模块核心结论）

**范式在所有模式下按需组合启用，不存在"某模式 = 某范式"的绑定**：

| 范式 \ 模式 | `ask` | `craft` | `plan` | `multi` |
|---|---|---|---|---|
| **ReAct**（循环底座） | ✅ 强制 | ✅ 强制 | ✅ 强制 | ✅ 强制 |
| **Reflection**（客观验证） | ➖ | ✅ 写后 headless 校验 | ✅ 节点完成判据 | ✅ per_task |
| **Plan-and-Solve**（DAG） | ➖ | ⚪ 模型隐式拆解 | ✅ 显式 DAG + 人审批 | ✅ 显式 + 并行拓扑 |
| **Multi-Agent**（编排） | ➖ | ➖ | ➖ | ✅ Orchestrator |

**图例**：✅ 引擎强制启用 / ⚪ 模型按实际需要自主决定 / ➖ 该模式下不适用

读法示例：
- **ReAct 是底座**——四模式全部强制启用，因为它是 M03 的循环本体，模式只是挂在其上的契约。
- **Reflection 在 ask 下不适用**——ask 没有写操作，没有可客观校验的产物（回答文案好坏无客观验证器）。
- **Plan-and-Solve 在 craft 下是"隐式"的**——craft 不出显式 DAG，但模型拿到"加存档系统"这种任务时会自主拆解子步骤；只是不强制出图、不强制人审批。
- **Multi-Agent 只在 multi 下启用**——这是编排形态维度，不是能力档位。

#### 代码铁证：plan 模式内部跑着 craft 子循环

```python
# plan.py:311-312 —— plan 的每个 DAG 节点，开一个 craft 子循环执行
result = await self.loop.run(
    session, node.prompt(graph.done_summary()), mode="craft")
```

这一行直接证伪了"模式=范式"的绑定：

**一次 plan 模式执行，同时用到三个范式**——
- **Plan-and-Solve**：外层 DAG 生成 + 人审批 + 拓扑推进
- **ReAct**：每个节点内部由 craft 子循环提供"想-做-看"循环
- **Reflection**：节点内每次写操作触发 headless 校验（craft 的 `VerifyLoop`）

同理，**ask 模式内部也在跑 ReAct**：模型问"lab 下有什么文件"→ 调 `list_files` → 看到结果 → 决定要不要再 `read_file` 某个文件 → 组织回答。这就是 ReAct，跟 craft 用的是同一个循环。

### 1.4 模式引擎实现：同一循环的策略对象

**① 严格定义**：模式 = 预置配置的策略对象（Strategy 模式），四维差异：**工具集**（`registry.filter` 视图）/ **采样参数**（temperature/top_p，M02 路由表）/ **循环钩子**（craft 挂 VerifyLoop、plan 挂 PlanGraph、multi 挂分发器）/ **系统提示模板**。`loop.py` 的 `run(mode=...)` 按注册表取策略装配——**新增模式 = 新策略类 + 注册，循环零改动**（注册表模式第三次落地）。

**② 大白话**：模式引擎本身也是"换挡器不是换发动机"——策略对象只改四个维度的配置，循环本体一行不动。这是"模式是产品概念不是技术分叉"在工程上的体现：Cursor 的自定义模式本质就是让用户写自己的 `ModeConfig` yaml。

**③ 举例**：策略基类把四维差异抽象成四个钩子，**基类给默认实现，子类按需重写**：

```python
class ModeStrategy(ABC):
    mode: str; config: ModeConfig
    @classmethod
    def tools_view(cls, registry) -> ToolRegistry: ...        # ① 工具集
    async def before_loop(self, session, task) -> list[Message]: ...   # ② 前置消息
    async def on_tool_done(self, tool, resp, session) -> str | None: ...# ③ 写后验证
    async def should_continue(self, session) -> bool: ...      # ④ 推进控制
```

| 模式 | 重写的钩子 | 效果 |
|---|---|---|
| `ask` | 无（全用默认） | 纯 ReAct + 只读契约 |
| `craft` | `on_tool_done` | ReAct + Reflection 验证回路 |
| `plan` | `before_loop` + 外循环 `run_plan_mode` | Plan-and-Solve 套在 ReAct 外 |
| `multi` | `before_loop` + `should_continue`（M15 补分发） | 编排形态切到并行 |

**④ 演进**：硬编码 `if mode ==`（每处散落）→ 配置文件 → 策略对象 + 注册表（本项目）。

**⑤ 易错点**：
- 钩子返回值的语义：`on_tool_done` 返回 `None` = 无反馈（放行），返回字符串 = 作为 Observation 注入下一轮。**不是所有模式都要重写它**。
- `should_continue` 是 plan/multi 的外循环扩展点，默认 `True`——单代理模式下不要动它。
- 注册表是**类级**注册（`PARADIGMS[cls.mode] = cls`），实例化在 `get_strategy` 时才发生，测试里可直接类调用 `PARADIGMS["ask"].tools_view(reg)`。

### 1.5 Plan-and-Solve 的工程落地（plan 模式详解）

**① 严格定义**：两阶段范式——先由模型产出**任务 DAG**（有向无环图：节点=子任务，边=依赖），经**人审批**（M09 确认门）后按**拓扑序**执行；节点失败触发 **re-plan**（带着失败上下文重新规划剩余部分，不推倒已完成）。提示层激发（Plan-and-Solve Prompting, Wang 2023）→ 工程层落地（本模块：结构化 DAG 而非文本计划）。

**② 大白话**：**先画施工图再盖楼**。直接砌墙（ReAct 一步一动）盖到三楼发现地基没打——返工代价惨重；plan 模式是先画依赖图（"打地基→[框架、水电]→封顶"，框架和水电可并行），**业主签字**后开工，顺序由图纸保证（拓扑排序=不拆承重先装窗户的事故免疫）。中途水电失败：不砸整栋楼重来（re-plan 只重排"未完工部分"，地基和框架保留）。

**③ 举例**：DAG 结构与执行器核心：

```python
@dataclass
class PlanNode:
    id: str; title: str; description: str
    depends: list[str]; status: Literal["pending","running","done","failed","skipped"]
    max_retries: int = 1

class PlanGraph:
    def ready_nodes(self) -> list[PlanNode]:          # 拓扑推进的核心
        """依赖全部 done 的 pending 节点（且无同层 failed 未处理）。"""
        return [n for n in self.nodes.values()
                if n.status == "pending"
                and all(self.nodes[d].status == "done" for d in n.depends)]
```

计划提示（让模型输出 JSON DAG）：要求**粒度 3~7 节点**（太细=DAG 里的 for 循环，浪费规划；太粗=失去并行机会）、每个节点写"完成判据"（给 re-plan 判断用）。

**④ 演进**：CoT 一步到位（错无回头）→ ReAct（边走边看，长任务漂移）→ Plan-and-Solve（2023：先全局规划）→ ReWOO（计划与执行解耦，计划期不消耗观察）→ LLM+PDDL（形式化规划器，选读）。工程落点：plan 审批是人类在环（HITL）范式在"任务级"的挂载。

**⑤ 易错点**：
- 模型给出的 DAG 可能**带环**（A 依赖 B 依赖 A）——解析时拓扑检测，带环直接打回重规划
- 计划幻觉（节点不可执行/依赖虚构）：每个节点审批时要人看"完成判据"是否可验证
- re-plan 上下文要带"已完成节点的产出摘要"，否则新计划会重复已完成步骤
- **plan 模式的"不写"仅指规划期**——批准后通过 craft 子循环执行，会真的改文件（别误以为 plan 是只读模式）

## 3. 关键难点参考片段：plan 模式主循环

拓扑推进 + 失败处理 + re-plan 的交织（挂在 M03 Loop 之外的一层外循环）：

```python
async def run_plan_mode(self, session, task: str):
    graph = await PlanGraph.from_task(self.llm, task)
    graph.validate_acyclic()
    if not await self.approver(graph.render_for_approval()):   # 人审批（任务级 HITL）
        return LoopResult("计划未获批准，已干净退出（无任何文件改动）",
                          0, None, "error")
    while True:
        ready = graph.ready_nodes()
        if not ready and graph.all_done():
            return LoopResult("全部节点完成", 0, None, "natural")
        if not ready:                                   # 有 failed 阻塞
            failed = next(n for n in graph.nodes.values() if n.status == "failed")
            await graph.replan_from(self.llm, failed)   # 带上下文重排剩余
            continue
        for node in ready:                              # 无依赖节点（M15 前先串行）
            result = await self.loop.run(session, node.prompt(), mode="craft")
            graph.mark(node.id, "done" if result.stop_reason == "natural" else "failed")
```

为什么难：**推进条件**（ready 空 ≠ 结束：可能是死锁阻塞）、re-plan 的上下文构造（已完成节点的产出摘要）、审批拒绝后的退出路径——三条状态流拧在一起，测试必须逐条覆盖。

注意最后一行 `mode="craft"`——**这是范式层组合的关键接缝**：plan 外循环（Plan-and-Solve）通过它把执行权交给 craft 子循环（ReAct + Reflection）。

## 7. 面试拷打（附详细参考答案）

**1. 模式（Ask/Craft/Plan/Multi）与范式（ReAct/Reflection/Plan-and-Solve）是什么关系？能 1:1 绑定吗？**

答：**两层正交，绝不能绑定**。模式是**产品层的"人机协作契约"**，回答"模型能做什么、做之前要不要问人"，由工具权限/审批门/自主度/编排形态四维刻画；范式是**技术层的"执行机制"**，回答"循环怎么组织、怎么纠错、怎么规划"。

不能绑定的铁证：本项目 `plan.py` 里 plan 模式的每个 DAG 节点都调用 `loop.run(mode="craft")` 开 craft 子循环——**一次 plan 执行同时用到 Plan-and-Solve（DAG）+ ReAct（节点内循环）+ Reflection（节点内写后校验）三个范式**。反过来说，ask 模式内部也在跑 ReAct（多轮检索：搜→看结果→决定再搜什么），只是手上没有写工具。

业界口径同样支持：CodeBuddy 官方解释说"**Craft 是核心的智能体模式，Ask/Plan 更像是在使用 Craft 时的两种提问策略**"——引擎是同一个，档位限制的是边界，不是引擎内部的运作方式。

正确的表述是**范式 × 模式矩阵**（§1.3）：ReAct 四模式强制启用（它是循环底座），Reflection 在 craft/plan/multi 启用、ask 不适用（无写产物可客观校验），Plan-and-Solve 在 plan 强制、craft 隐式（模型自主拆解但不强制出图），Multi-Agent 只在 multi 启用。判断用不用某个范式的依据是**当前这一步的实际问题**，不是外壳叫什么模式名。

**2. Plan-and-Solve 与 ReAct 的适用分界？**

答：任务结构决定范式选择。ReAct 强项：探索型、步骤不可预知（"看看这个项目有什么问题"——看什么取决于每步看到什么）；弱项：长任务目标漂移（20 轮后忘了初心）+ 无并行（天然串行）。Plan-and-Solve 强项：目标明确、子任务有依赖结构（"加存档系统"=可预先分解为配置/序列化/UI 三块）；弱项：探索型任务计划无意义（计划赶不上变化，re-plan 成本反噬）。工程判据：**能写出 3~7 个"完成判据明确"的子任务就用 plan，否则 ReAct**。四模式让用户/路由器（M12）按任务形态选。

**3. 为什么选"客观验证器"而不是模型自评做 Reflection？**

答：可靠性排序：客观验证器>互评>自评。自评的系统性偏差：模型给自己的输出打分倾向高分（训练目标使然——RLHF 优化的是"看起来好"），且缺乏可执行的判断标准；自评唯一的用途是低成本初筛。客观验证器（headless 校验/编译/测试）的优势：判定可复现（同输入同结论）、错误带定位（行号/断言），修复信号强——craft 模式选择它是因为**代码的"对错"恰好可机器判定**（这是领域运气：Git 代码是少数有免费验证器的领域）。反例：文案好坏无客观验证器，只能退互评/人评。

**4. DAG 为什么要人审批？审批看什么？**

答：审批是任务级的 HITL（M09 是操作级）。看三点：①**节点粒度**（3~7 个，太细说明模型在 DAG 里写 for 循环）②**完成判据**（每节点"怎么算完成"是否可验证——不可验证的判据执行时无法判定 done）③**依赖结构**（有没有"其实无依赖却被串行"的浪费并行机会/有没有幻觉依赖虚构的文件）。审批的成本收益：一次审阅 30 秒 vs 计划错误执行 10 分钟后返工——**纠错成本随执行深度指数增长**，在源头拦最便宜。

**5. re-plan 为什么不推倒重来？要带什么上下文？**

答：不推倒：已完成节点的产出（文件、配置）是真实资产，重做烧钱且可能与已落盘产物冲突（乐观锁连锁冲突）。带的上下文三样：①已完成节点的清单+产出摘要（新计划必须跳过/衔接它们）②失败节点的**完整错误上下文**（不是"失败了"三个字——错误 Observation 原文，否则新计划重蹈覆辙）③原始任务目标（防多轮 re-plan 后目标漂移）。工程细节：`replan_from` 只重新生成"失败节点及其后代"的子图，前驱保持。

**6. 四模式的技术本质是什么？如何新增一个模式？**

答：本质=**同一 ReAct 循环上的"契约配置"**：工具集视图（`registry.filter`）+ 采样参数 + 循环钩子（验证回路/计划推进）+ 系统提示。**不是四套算法，是四组边界配置**——这是"模式是产品概念不是技术分叉"的工程体现。

新增模式三步：写 `ModeStrategy` 子类（差异化只动钩子）+ `@register` 注册 + 产品入口暴露（CLI 参数/Web 切换器）。循环代码零改动——这是策略模式+注册表（第三次复用）的组合收益。

面试加分：指出 Cursor 的自定义模式本质就是让用户写自己的 `ModeConfig` yaml；本项目 M19 设置页可沿用同样思路。

**7. craft 的验证为什么分级（L1 每次/L3 关键节点）？**

答：成本-收益匹配。L1 语法校验秒级、拦住最高频错误（缩进/未定义变量）——每次写后跑，性价比极高；L2 导入秒~分钟、拦资源断链；L3 测试套件分钟级——每次写后跑会让一个 5 步任务多花 5 分钟，只在"节点完成"（plan 的节点边界）或用户显式要求时跑。这与 CI 的分层（pre-commit 秒级/pre-push 分钟级/流水线小时级）同构——**反馈速度与检查深度的阶梯设计**。

实现四个要点（分级对照见 §1.2 末尾的表）：

1. `ModeConfig.verify` 是**累积档**：`"L1"`=L1，`"L1+"`=L1→L2，`"L3"`=L1→L2→L3——不是"只跑某一级"，命名最容易在这里读错。
2. **顺序必须 L1 → L2 → L3**：新建资源不先 `--import`，后续校验会集体误报"资源不存在"（Godot 资源缓存未构建，M06 §7.6）。
3. **L4 不入 `verify`**：跑场景有副作用（截图/改游戏状态）且需用户确认，只能显式调用 `runner.run_scene()`。
4. **鸭子类型降级**：runner 未实现某级方法则跳过该级继续，不报错——保证四级齐全的真实 `GodotRunner` 与只有 `check()` 的极简 runner 都能跑同一份 `VerifyLoop`。

**8. 计划幻觉（不可执行节点/虚构依赖）怎么防？**

答：四道防线：①生成时提示约束（每节点必须绑定"完成判据"+判据必须是可观察的：文件存在/校验通过/测试绿）②结构校验（无环+依赖引用的节点存在+节点数 3~7）③**人审批**（最后一道，也是最有效的——人对"这计划靠不靠谱"的直觉远超规则）④执行期容错（节点跑完判据不满足→标记 failed→re-plan，而不是硬着头皮往下走）。承认计划幻觉不可能根除（模型对项目现状认知有限），防线设计成纵深——这也是"验证文化"从代码延伸到计划的体现。

**9. multi 模式在 M13 与 M15 的分界？**

答：M13 提供骨架：模式注册（配置维度 per_worker/plan_first）+ 降级路径（无 Orchestrator 时退化为 plan 串行）；M15 提供血肉：Orchestrator-Worker 分发器、子代理上下文隔离、结果聚合、A2A 协议。分界的工程理由：模式引擎（配置/注册/钩子）与并行执行器（进程/任务管理）是**正交关注点**——分两模块各自演进，M13 完成时 multi 可用（串行版），M15 完成时变并行（接口不变）。

**10. 为什么把 Multi 做成独立模式？Cursor 明明把它放在 Agents Window 里。**

答：Cursor 的多 agent 并行确实是"窗口能力"而非"模式"——3.0 的 Agents Window 让每个 agent tab 持有自己的 mode/model/worktree，3.2 的 `/multitask` 让异步子代理并行。

本项目把它提为显式模式，权衡是：**可发现性 > 概念纯度**。用户看到模式切换器上有 multi，一眼就知道"我现在是单干还是派车队"；放在窗口里则要靠用户去发现。代价是模式切换器多一档，且要解释清楚"multi 是编排形态维度，不是能力档位维度"——它和 craft 不是并列的"能力等级"，而是"同样的能力，换并行执行"。

技术上 `multi` = `per_worker` 工具视图 + `plan_first` + 并行编排（M15），内部仍按需组合 ReAct/Reflection/Plan-and-Solve，符合 §1.3 矩阵。

**11. ToT（Tree of Thoughts）与 plan 模式的关系？**

答：ToT 是 plan 的"搜索化"版本：不是生成一个计划，而是生成 k 个候选分支、每步评估打分、保留 top 分支继续扩展（beam search 式推理树）。适用：解空间大且步进可评估的任务（数学题/谜题）；不适用：工程任务（分支执行有真实副作用，回溯成本不是 token 是文件系统——M06 检查点回滚远比"换个分支"贵）。本项目的工程化近亲：plan 模式的多候选方案对比（审批视图给 2 个方案让人选）借了 ToT 的"分支生成"思想，砍掉"自动回溯"（副作用领域回溯要人批）。选读论文，思想收编，机制不用。

**12. 开放题：模式自动选择（Auto 模式）怎么设计？**

答：三段设计：①信号源——M12 意图分类已有 code_edit/knowledge 分流（Auto 的雏形），扩展信号：任务长度预估（首句+项目规模→长任务倾向 plan）、历史模式使用效果（同类任务 craft 三次失败→下次建议 plan，M08 记忆的用武之地）；②决策器——规则优先（明确 code_edit→craft）+小模型兜底（四分类，同 M12 意图分类器复用）；③透明性与否决权——Auto 的选择必须展示且一键切换（"已选 craft，切换？"）——自动化的前提是可否决，否则一次误判毁信任。演进路径：Auto 先做"建议"（弹推荐让人确认）再做"默认"（置信度>阈值才自动）——灰度思想一以贯之。
