## 1. 知识点详解（每节五段：定义 → 大白话 · 举例 · 演进 · 易错点）

### 1.1 JWT 认证与 RBAC

**① 严格定义**：JWT 三段式 `header.payload.signature`——payload 含 `sub/tenant_id/role/exp`，签名防篡改。**无状态验证**（服务端不查会话表，验签即认）换来水平扩展自由，代价是**撤销难**——所以 access token 短命（15min）+ refresh 长命（7d，服务端可撤销，旋转式：用一次发新）。三级凭证：JWT access（Web 交互）/JWT refresh（仅 refresh 端点）/API Key（程序调用，hash 存库）。RBAC 四角色矩阵（owner/admin/dev/viewer）硬编码 `rbac.py`。

**② 大白话**：**酒店房卡体系**。access token=房卡：开箱即用无需查库（无状态验签=读卡器离线也能验卡内芯片），但丢了不能挂失（撤销难）——所以房卡有效期只有一天（15min），过期拿长住证（refresh token，前台有登记可作废）换新卡。**tenant_id 必须刻在卡里**（token payload）而不是住客口头报——前台听住客说"我住 8 楼"就给 8 楼权限，是最大的越权洞。

**③ 举例**：依赖注入式鉴权（FastAPI 惯用法，可直接参考）：

```python
async def current_actor(cred = Depends(security), db=Depends(get_db)) -> Actor:
    payload = jwt.decode(cred.credentials, SECRET, algorithms=["HS256"])   # 验签
    if await revoked(jti=payload["jti"]): raise HTTPException(401, "已撤销")
    return Actor(user_id=payload["sub"], tenant_id=payload["tenant_id"], role=payload["role"])

def require(*perms):                       # 路由侧一行声明
    def dep(actor = Depends(current_actor)):
        if not rbac.has(actor.role, *perms): raise HTTPException(403)
        return actor
    return dep
```

**④ 演进**：session cookie（有状态、CSRF 烦）→ JWT（无状态、撤销难）→ access+refresh 双 token（折中主流）→ opaque token+Redis（可撤销回归，大厂内部常用）。面试要点：**讲清"无状态便利 vs 撤销能力"的取舍链**。

**⑤ 易错点**：
- JWT payload 只是 base64 **不是加密**——别放敏感信息（邮箱可以手机号不要）
- `tenant_id` 必须来自 token 而非请求参数——前端传什么 tenant 就用什么=水平越权经典
- SECRET 走环境变量；测试环境独立密钥；泄漏过的密钥立即轮换

### 1.2 多租户数据隔离（共享表 + tenant_id）

**① 严格定义**：三种隔离模型——独立库/租户（隔离强成本高：连接/迁移×N）、独立 schema/租户（中间态）、**共享表+tenant_id**（隔离弱靠查询纪律，成本低，本项目选它——个人/小团队产品定位）。共享表的命门：**每条查询必须带 tenant_id 过滤**，漏一条就是数据泄漏。

**② 大白话**：**共享办公室的工位分区**。独立库=每家公司独栋楼（最安全最贵）；共享表=大家在同一层办公，靠工位牌（tenant_id）划地盘——**保安巡逻（查询过滤）漏查一次，A 公司就能翻 B 公司的文件柜**。三道防线：①工位牌强制佩戴（ORM 基类自动注入，想漏都难）②监控抽查（SQLAlchemy 事件钩子审计"无 tenant 条件的查询"）③演习（双租户集成测试断言互不可见）。

**③ 举例**：仓储基类（让遗漏结构性不可能）：

```python
class TenantRepository(Generic[T]):
    def __init__(self, model: type[T], actor: Actor): ...
    def query(self, db: Session) -> Query:
        return db.query(self.model).filter(self.model.tenant_id == self.actor.tenant_id)
    # 所有业务查询从 self.query() 出发——tenant 过滤不可能被"忘记"
    # 跨租户管理员操作走显式 AdminRepository（代码评审重点盯防）
```

**④ 演进**：单租户部署（每客户一套）→ 共享表（SaaS 起步标配）→ schema 隔离（合规要求客户）→ 混合（大客户独立小客户共享）。**隔离模型是产品/合规决策不是纯技术决策**。

**⑤ 易错点**：
- JOIN 表漏 tenant 条件（主表过滤了 JOIN 出来的行没过滤）——用 ORM 关系而非手写 JOIN
- **全局缓存键必须带 tenant 前缀**——缓存泄漏比查询泄漏更隐蔽
- Celery worker 无请求上下文——Actor（含 tenant_id）随任务参数显式传递

### 1.3 SSE 网关与连接管理

**① 严格定义**：`POST /sessions/{id}/messages` 返回 `text/event-stream`——AgentService 把核心包 EventBus 实时转发。三大工程问题：**断线重连**（每事件带 `id:` 单调递增→客户端重连带 `Last-Event-ID`→hub 环形缓冲 256 帧补发）、**背压**（慢客户端 10s 不消费主动断开——不能让它堵死核心包队列级联雪崩）、**心跳**（每 15s `: ping` 注释帧过中间件 idle 超时）。环形缓冲三层清理：run 结束 TTL 60s 延迟清（不能立即删：用户可能断线 1s 后才重连，恰是最需补发的时刻）/会话关闭即清/deque maxlen 自限。

**② 大白话**：hub 是**前台寄存处**。客人（浏览器）中途出去接电话（断网），回来凭取件号（Last-Event-ID）取走错过的包裹（补发帧）；寄存架只有 256 格（环形淘汰），包裹保留一小时（TTL）后清理——**立即扔掉刚到的取件需求是最蠢的时机错配**。慢客户端像堵在柜台不走的客人——礼貌请离（主动断开），不能让后面所有人陪着堵。

**③ 举例**：hub 的环形补发（含清理时机，可直接参考）：

```python
class SSEHub:
    def __init__(self, replay_size=256):
        self.ring: dict[str, deque] = {}          # ★不用 defaultdict：查询会凭空建空 deque（慢性泄漏）
        self._purge_tasks: dict[str, asyncio.Task] = {}
    def touch(self, sid):                          # 新帧到达即取消待清理（流还活着）
        if (t := self._purge_tasks.pop(sid, None)): t.cancel()
        self.ring.setdefault(sid, deque(maxlen=self._replay_size))
    async def replay_from(self, sid, last_id):
        ring = self.ring.get(sid)                  # ★查询不创建
        return [f for f in (ring or []) if f.id > last_id]
    async def close_run(self, sid, ttl=60.0):      # TTL 延迟清理
        async def _purge(): await asyncio.sleep(ttl); self.ring.pop(sid, None)
        self._purge_tasks[sid] = asyncio.create_task(_purge())
```

**④ 演进**：短轮询（延迟差）→ WebSocket（全双工但重）→ **SSE**（单向流的正确工具：HTTP 原生/自动重连/经得起企业代理）→ HTTP/2 多路复用。口诀：**客户端只收不发选 SSE，双向实时才上 WS**。M21 演进：Redis Stream（多实例共享补发、重启不丢）。

**⑤ 易错点**：
- 发布/重载时 SSE 全断——前端"重连+拉增量"配合（M20 useSSE 与 replay 对齐）
- 确认门挂起 24h 期间 SSE 保持开放但无事件——心跳帧就是为这窗口准备的
- **ring 只增不减=慢性泄漏**：defaultdict 查询建空 deque、run 结束不清——查询用 `.get`、清理走 TTL+会话关闭两路
- 环形缓冲≠历史记录：它只服务秒~分钟级补发，历史在 messages 表——两层职责别混

### 1.4 异步任务（Celery）与配额计量

**① 严格定义**：两类活必须出主进程：**慢活**（嵌入构建 10 分钟/训练数小时——HTTP 请求里做完必超时）与**定时活**（记忆 GC/检查点清理）。Celery 三件套：broker（Redis）排队、worker 执行、beat 定时。**配额计量**：中间件在请求结束把 usage（来自 LoopResult）写 `usage_records` 表；配额检查在下一请求入口（余额不足 429）。原则：**计量在出口（权威数据来自网关 usage），配额在入口（拦截新请求）**——超限一点点是设计允许的（不做硬实时扣减，那是数据库热点）。

**② 大白话**：**后勤外聘团队**。前台（web 进程）只接单不搬货——搬钢琴（嵌入构建）外包给搬运队（worker），单子贴在传菜窗口（broker 队列）；每天凌晨的保洁（GC）由排班表（beat）触发。计费像水电表：**用量在表出口计量**（这次任务实际用了多少），**闸刀在进户口**（下次开门前查余额）——不做"每滴水流过都实时扣费"的硬实时（水表狂转数据库热点），月底"多用一点点"是可接受的账期误差。

**③ 举例**：幂等键防重复入队：

```python
task = embed_document.apply_async(
    args=[actor.tenant_id, doc.id],
    task_id=f"embed:{doc.id}")          # ★固定 task_id=幂等键：重试/重传不产生双份构建
```

**④ 演进**：线程池（单机）→ Celery（分布式标准）→ arq/dramatiq（轻量）→ K8s Job/Argo（云原生）。选 Celery：生态成熟+beat 够用。

**⑤ 易错点**：
- worker 依赖必须与 web 同镜像（版本漂移的隐性 bug）——CI 一并构建
- 任务里不能用请求级 Actor——系统身份+显式 tenant_id
- beat 时区：容器默认 UTC，cron 按业务时区写清（凌晨 3 点的 GC 是哪个 3 点？）

## 3. 关键难点参考片段：SSE 生成器的生命周期

客户端断开时 StreamingResponse 生成器收到 GeneratorExit——必须清理订阅与后台 task：

```python
async def stream_message(...):
    sub = hub.subscribe(session_id)
    task = asyncio.create_task(engine.run(...))
    try:
        yield "retry: 3000\n\n"
        for frame in await hub.replay_from(sid, last_id):
            yield frame
        async for ev in sub:
            yield sse_format(ev)
    finally:
        await hub.unsubscribe(sub)                  # ★断开必清
        if not task.done():
            task.cancel()                           # 策略：连接死→任务取消（可 /resume 续跑）
            with suppress(asyncio.CancelledError):
                await task
```

为什么难：三个异步体（HTTP 连接/事件订阅/Agent 任务）生命周期各不相同——**"谁跟着谁死"是策略问题**，策略错任一处就是协程泄漏或僵尸任务。

## 7. 面试拷打（附详细参考答案）

**1. JWT 无状态的代价？双 token 怎么补救撤销？**
答：无状态=服务端验签即认、不查会话表——收益是水平扩展自由（任何实例都能验任何 token，无需共享会话存储）与读性能；代价是**撤销难**：签发后到 exp 前始终有效（用户登出/被盗号，token 依然能用）。双 token 补救：access 短命（15min）——撤销窗口最多 15 分钟；refresh 长命但**有状态**（存表可作废，且旋转式：每用一次发新的并作废旧的——被盗的旧 refresh 立即失效）。风险窗口收窄到"单个 access 的 15 分钟"，而"随时踢人下线"由 refresh 撤销达成。附加手段：jti 黑名单（登出时把当前 access 的 jti 进 Redis 到 exp 过期）——用极小的有状态成本换即时撤销。

**2. tenant_id 为什么必须来自 token？水平越权的经典路径？**
答：信任边界原则：token 是**服务端签发并签名**的（可信），请求参数是**客户端可任意构造**的（不可信）。经典攻击路径：GET /projects/123/files?tenant_id=456——如果服务端信了参数里的 tenant_id，攻击者改参数就能以自己的合法 token 读任意租户的数据（**水平越权**：认证过了但越了授权边界）。正确实现：tenant_id 只从 token payload 解出（current_actor），全程从 Actor 取，请求参数里的 tenant 字段直接忽略。测试守门：双租户数据+参数化遍历端点断言 404（不是 403——404 不暴露资源是否存在，防探测枚举）。

**3. 共享表 vs schema 隔离 vs 独立库的决策维度？**
答：四个维度：①**隔离强度需求**——合规（医疗/金融大客户）要求物理隔离→独立库/schema；一般 SaaS 逻辑隔离够→共享表；②**成本**——独立库：连接池/迁移/备份 ×N，租户数过百后运维爆炸；共享表一套设施；③** noisy neighbor**（吵闹邻居：一个租户打爆数据库影响全体）——独立库天然免疫，共享表要靠限流（M19 配额中间件）；④**迁移演进**——共享表起家后期要拆（大客户转独立）需要数据搬移管道；独立起家合并几乎不可能。本项目共享表：个人/小团队定位、租户量可控、成本最优先。面试加分：指出这是**产品/合规决策**（定价分层：企业版=独立部署）不是纯技术选型。

**4. 仓储基类自动注入怎么"让遗漏不可能"？JOIN 的漏洞？**
答：机制：所有业务查询的入口收敛到 `TenantRepository.query()`——它在第一层就 `.filter(tenant_id==actor.tenant_id)`，业务代码在其上叠加条件——**不调用这个入口就无法查库**（代码评审规则：模型对象不许直接出现在 service 层），遗漏在结构上不可能（不是靠人记纪律而是靠 API 形状）。JOIN 漏洞：手写 JOIN 时主表过滤了、JOIN 出来的从表行没过滤（`join(Session.messages)` 出的消息行没带 tenant 条件）——缓解：用 ORM 的 relationship（关系查询自动继承父表的过滤链）；彻底方案：SQLAlchemy 事件钩子审计最终 SQL，发现"涉及租户表但无 tenant 条件"的语句告警（防线 2）。

**5. SSE vs WebSocket 选型判据？补发缓冲为什么不能在 message_end 立即删？**
答：判据一句话：**客户端只收不发选 SSE，双向实时才上 WS**。SSE 优势：HTTP/1.1 原生（企业代理/防火墙友好）、浏览器内置自动重连（EventSource 语义）、每帧带 id 的补发协议标准化；WS 优势：双向低延迟（协同编辑/语音）。补发缓冲不能立即删的原因：**最需要补发的时刻恰是 run 刚结束的瞬间**——用户看到回答快结束时网络闪断，1 秒后重连带 Last-Event-ID，如果 message_end 一到就清了 ring，最后几帧（含 usage 统计）永远丢了。TTL 60s 是"断线重连的典型窗口"与"内存占用"的折中——三层保险（TTL/会话关闭/maxlen）覆盖所有清理时机。

**6. 慢客户端背压为什么必须服务端主动断开？雪崩传导链？**
答：传导链：慢客户端（浏览器后台标签页节流/弱网）不读响应→TCP 缓冲满→生成器 yield 阻塞→该连接的协程挂起→若事件来自共享队列（hub 广播），**一个订阅者不消费会堵住发布者**→核心包 EventBus 的 queue 满→Agent Loop 的 emit 阻塞→**所有会话的 Agent 都卡住**——单点慢变成全局雪崩。主动断开（10s 未消费）=切掉坏肢体保全身：该客户端重连后走 replay 补发，数据不丢只是连接重建。设计原则：**流式系统的每一级都要有"丢弃慢消费者"的预案**（Kafka consumer lag 淘汰、nginx proxy_buffer 落盘上限，同思想）。

**7. 三个异步体断开时的清理策略？**
答：三个异步体生命周期：HTTP 连接（用户关页面即断）、事件订阅（hub 的订阅协程）、Agent 任务（engine.run 的 asyncio.Task）。策略矩阵：连接死→订阅必清（unsubscribe，否则 hub 泄漏）；连接死→任务**取消**（当前选择：会话可 /resume 续跑，任务状态已持久化在事件流里——M09 的恢复能力让"取消"是安全的）；若产品要求"关页面任务继续跑"则改为**不取消**（任务完成后结果落库，用户回来拉增量）——两种策略都成立，关键是**显式选择并全链路一致**。错误示范：不清理（协程泄漏）或只 cancel 不 await（取消未完成，task 成为僵尸）。

**8. 计量在出口、配额在入口，为什么不做硬实时扣减？**
答：硬实时扣减（每次 usage 写入时同步检查余额+扣减）的问题：①数据库热点——usage_records 是高频写入表（每轮对话多条），余额检查扣减把它变成"每写必锁"的竞争点；②一致性成本——分布式下要事务/锁保证"余额不为负"，并发边界复杂；③用户体验反而差——长任务跑到一半余额耗尽被强杀（半成品比超一点更糟）。出口计量+入口配额：写入只 append（无锁），配额在**新请求入口**异步汇总检查——允许"最后一个任务超限一点点"（账期误差），换来写入零竞争与任务完整性。这是计费系统的通用模式（运营商流量月结同理）。

**9. Celery 幂等键怎么设计？worker 租户上下文从哪来？**
答：幂等键：`task_id=f"embed:{doc.id}"`——Celery 同 task_id 的任务不重复入队，重试/用户重复点击/前端重传都收敛到同一次执行。设计原则：**业务实体天然键**（doc_id/job_id）而非随机 uuid；一个实体一个任务生命周期。租户上下文：worker 进程没有 HTTP 请求（没有 Depends 注入的 Actor）——**唯一正道是任务参数显式携带**：`apply_async(args=[tenant_id, doc_id])`，任务内部第一行 `actor = Actor.system(tenant_id)` 构造系统身份，全程仓储过滤基于它。反模式：用线程本地变量/全局变量传租户（worker 是多进程复用，串号是必然事故）。

**10. 开放题：单区域到多区域，这套架构最先崩的是哪里？**
答：三处按崩溃顺序：①**SSE 有状态连接层**最先崩——hub 的环形缓冲在进程内存，多区域部署后用户的重连可能落到另一区域（缓冲不在那，补发失败）——解法：连接层网关+Sticky Session（同用户路由同区域）或缓冲外置（Redis Stream 全局共享，M21 预留的演进路径正好接上）；②**跨区写延迟**——MySQL 单主跨区写 RTT 数十毫秒，会话高频写变成慢查询——解法：读写分离（各区只读副本+本区写转发）到最终按租户分区（tenant_id 哈希到区域，租户内强一致）；③**Celery/Redis 的局域网假设**——broker 跨区访问的队列延迟与连接稳定性——解法：任务按租户区域亲和调度。架构判断顺序背后的原则：**先崩的都是"隐性单点假设"（内存态、单主、局域网）——多区域化的本质是把每个隐性假设显式化并付分布式成本**。
