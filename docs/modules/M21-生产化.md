## 1. 知识点详解

### 1.1 可观测三支柱：Logs · Metrics · Traces

**① 原理**

三支柱各自回答一个问题、互相索引：

```text
Metrics（数字，回答"正常吗"）
  技术指标：http_qps · http_p99_latency · sse_active_connections
  业务指标：agent_tokens_total{model,tenant} · tool_calls_total{tool,status}
           · confirm_gate_wait_seconds · rag_recall_score（采样）
Logs（文本，回答"发生了什么"）
  结构化 JSON（structlog）：request_id/tenant_id/session_id 全程携带
  —— 日志必须能被 trace_id/metric label 索引到，三者是同一事实的三种投影
Traces（因果树，回答"慢在哪/断在哪"）
  一次 craft 请求的 Span 树：
  POST /messages (2.3s)
   ├─ query_engine.process (180ms)
   │   ├─ intent.classify (210ms→含一次 llm call)
   │   └─ rag.retrieve (95ms) ── milvus.search (60ms)
   ├─ agent_loop.step#1 (1.9s)
   │   ├─ llm.stream (1.2s) ── provider=deepseek
   │   └─ tools.godot_check (610ms) ── subprocess
   └─ sse.flush (3ms)
```

**OTel 装配**：FastAPI 自动 instrumentation（HTTP 层）+ 手动 span（`agent_loop`/`tool` 边界）+ **把 M03 的 AgentEvent 事件流桥接为 span attributes**（tool name/usage 进 span）——核心包仍是纯库：它只发事件，OTel 适配器在应用端订阅事件生成 span（M00 依赖规则的又一次兑现）。

**② 演进**：printf 日志（人肉 grep）→ 三支柱标准（Google SRE 推动的事实标准）→ OpenTelemetry 统一 SDK（厂商中立采集）→ exemplars（metric 指向具体 trace 的关联点）。面试锚点：**三者不是三套系统，是同一请求事实的三种查询接口**。

**③ 最小案例**：中间件埋 trace 上下文

```python
@app.middleware("http")
async def observability_mw(request, call_next):
    rid = request.headers.get("X-Request-ID", new_id())
    tid = current_trace().trace_id
    structlog.contextvars.bind_contextvars(request_id=rid, trace_id=tid,
                                           tenant_id=get_tenant_or_none(request))
    with tracer.start_as_current_span("http.request") as span:
        span.set_attribute("http.route", request.url.path)
        t0 = time.perf_counter()
        try:
            resp = await call_next(request)
        finally:
            hist.labels(route=request.url.path, status=resp.status_code
                        if 'resp' in dir() else 500).observe(time.perf_counter() - t0)
        return resp
```

**④ 易错点**
- P99 要用直方图（histogram）服务端分桶计算，不是把所有延迟存下来再排序（内存爆炸）
- 高基数 label 是 Prometheus 杀手（session_id 做 label = 时序数据库爆炸）——高维信息进 logs/traces，metric label 只留低基数（route/model/tenant 级别）
- SSE 长连接的"延迟"定义特殊（首字节延迟 TTFB 才是用户感知），别把连接时长当延迟统计

### 1.2 分布式限流：Redis + Lua 滑动窗口

**① 原理**

M02 的令牌桶是**单进程**的——多副本部署下每 Pod 独立限流=配额×N。分布式限流把计数搬到 Redis，**Lua 保证"读-改-写"原子性**（Redis 单线程执行 Lua 脚本期间不插入其他命令）：

```lua
-- rate_limit.lua：滑动窗口（精确版）
-- KEYS[1]=限流键  ARGV: now, window_ms, limit, cost
local key = KEYS[1]
redis.call('ZREMRANGEBYSCORE', key, 0, ARGV[1] - ARGV[2])   -- 清理窗口外
local count = redis.call('ZCARD', key)
if count + ARGV[4] > tonumber(ARGV[3]) then
  return 0                                                   -- 拒绝
end
redis.call('ZADD', key, ARGV[1], ARGV[1] .. '-' .. math.random())
redis.call('PEXPIRE', key, ARGV[2])
return 1                                                     -- 放行
```

**限流维度**（产品语义）：租户级 RPM/TPM（套餐配额）、用户级并发会话数、全局下游保护（对 DeepSeek API 的总并发——成本护栏）。**429 响应必须带 Retry-After**（M02 客户端重试链的另一半）。

**② 演进**：进程内锁（单机）→ Redis INCR+EXPIRE 固定窗（边界突刺：窗口切换瞬间双倍流量）→ 滑动窗口 ZSET（精确但内存 O(活跃请求)）→ 令牌桶 Lua（省内存允许突发）→ 网关层限流（nginx limit_req / 云 WAF）。本项目：租户配额用滑动窗口（精确计费语义），全局保护用令牌桶（突发友好）。

**③ 最小案例**：Python 调用侧

```python
class RedisRateLimiter:
    def __init__(self, redis, script=load_lua("rate_limit.lua")): ...
    async def allow(self, key: str, limit: int, window_ms: int, cost: int = 1) -> bool:
        ok = await self.redis.eval(self.script, 1, key,
                                   int(time.time() * 1000), window_ms, limit, cost)
        return bool(ok)
    # 拒绝时从 ZSET 里算最早放行时间 → Retry-After
```

**④ 易错点**
- Lua 脚本必须**无副作用确定性**（禁止 random？——上面用了 random 做成员去重，可换成 INCR 序号，稳妥）
- Redis 挂掉限流怎么办：**fail-open**（放行+告警，可用性优先）还是 fail-close（拒绝，保护优先）——按业务定，本项目配额限流 fail-open（短期超一点可接受），下游保护 fail-close（模型 API 烧钱）
- ZSET 成员唯一性：同毫秒多请求成员冲突 → 计数偏小（限流变松）

### 1.3 压测与容量规划

**① 原理**

Agent 平台压测的特殊性：**负载不是 QPS 而是"并发会话 × 每会话步数"**，且下游（LLM API）延迟秒级、成本真金白银。策略：

```text
压测目标三问：
  1. 单 Pod 多少并发 SSE 会话稳定？（连接+协程内存）
  2. 工具执行洪峰（headless 100 并发）会不会打爆 CPU/磁盘？
  3. 降级链路真的降级吗？（mock LLM 挂掉 → 熔断 → fallback 生效？）
工具：k6（HTTP/SSE 场景）+ mock LLM 服务（本地起 vLLM 跑 0.5B 或响应回放器）
     ——回放器：录真实事件流按序回放，压"我们的系统"而不是"别人的 API"
核心指标：SSE TTFB P99 < 1s · 事件吞吐 · 会话建立成功率 · 内存 RSS 增长曲线（泄漏检测）
容量推算：压出单 Pod 200 并发会话 → 目标 5000 并发 → 25 Pod + 30% 冗余 → HPA min 10 max 40
```

**② 演进**：ab/wrk（裸 HTTP）→ locust（Python 场景）→ k6（JS 脚本、SSE 支持好）→ 混沌工程（Chaos Mesh 注入故障验证韧性）。**从"测吞吐"到"验降级"是生产压测的成熟标志**。

**③ 最小案例**：k6 SSE 场景骨架

```javascript
// benchmarks/k6/sse_chat.js
import http from 'k6/http';
export const options = {
  scenarios: { chat: { executor: 'ramping-vus',
    stages: [{ duration: '2m', target: 50 }, { duration: '5m', target: 200 }] } },
  thresholds: { 'http_req_duration{endpoint:messages}': ['p(99)<1500'] },
};
export default function () {
  const token = __ENV.TOKEN;
  const resp = http.post(`${__ENV.BASE}/api/v1/sessions/1/messages`,
    JSON.stringify({ content: '列出文件' }),
    { headers: { Authorization: `Bearer ${token}` }, timeout: '60s' });
  check(resp, { 'sse ok': r => r.status === 200 });
}
```

**④ 易错点**
- 别拿生产 API key 压（成本事故）——mock LLM 或沙箱账号
- 长连接压测的 VU≠并发连接：k6 每虚拟用户同时间一个连接，模型对准"并发会话数"
- 泄漏看曲线不看瞬时：SSE 会话建立/断开 1000 轮后 RSS 是否回落（事件订阅/hub 清理 bug 在这里现形）

### 1.4 K8s 部署与无状态化改造

**① 原理**

部署拓扑（deploy/k8s/）：

```yaml
# 核心清单（节选要点）
apiVersion: apps/v1
kind: Deployment            # web：无状态多副本
spec: template: spec:
  containers:
  - name: web
    resources: { requests: {cpu: 500m, mem: 1Gi}, limits: {cpu: "2", mem: 2Gi} }
    readinessProbe: { httpGet: {path: /health/ready, port: 8000} }   # 就绪≠存活
    livenessProbe: { httpGet: {path: /health/live, port: 8000} }
---
apiVersion: autoscaling/v2
kind: HPA                   # 按 CPU + 自定义指标（活跃 SSE 连接数，adapter 暴露）
spec: { minReplicas: 3, maxReplicas: 40,
        metrics: [{type: Pods, pods: {metric: {name: sse_active_connections},
                                      target: {averageValue: "150"}}}] }
---                          # worker：Celery 独立 Deployment（队列积压指标扩缩）
---                          # godot-runner：headless 执行专用池（污点节点：本地盘+高CPU）
```

**无状态化三改造**（从 compose 到 K8s 的真正工作量）：

```text
1. 本地文件状态外移：SQLite→MySQL（仓储实现已双轨，M00 端口-适配器兑现）
   Godot 项目目录→共享存储（RWX PVC/NFS）或对象存储按需拉取+检查点化
2. SSE 连接的可漂移性：Pod 挂了连接断 → 前端 Last-Event-ID 重连到任意 Pod
   → hub 环形缓冲搬到 Redis（补发不依赖原 Pod）★这是本项目最大的改造点
3. 定时任务防重：beat 单副本 + 分布式锁（M19 已有 Redis 基建）
```

**② 演进**：docker-compose 单机（开发）→ K8s 声明式（自愈/伸缩/滚动发布）→ Helm/Kustomize（环境参数化）→ GitOps（ArgoCD）。**项目就到 K8s+Kustomize**（个人项目边界，Helm 选读）。

**③ 最小案例**：hub 缓冲 Redis 化的关键行

```python
class RedisSSEHub(SSEHub):
    async def publish(self, sid: str, ev: AgentEvent):
        await self.redis.xadd(f"sse:{sid}", {"id": self._next_id(sid),
                                             "data": ev.json()}, maxlen=256)
        await self.redis.expire(f"sse:{sid}", 86400)
    async def replay_from(self, sid, last_id) -> list[str]:
        return [frame for frame in
                (await self.redis.xrange(f"sse:{sid}", min=f"({last_id}"))]
    # 任意 Pod 都能补发任何会话的历史帧 → 连接漂移自由
```

**④ 易错点**
- readiness 与 liveness 别用一个探针：慢启动（模型/索引加载 30s）会被 liveness 误杀循环重启
- 滚动发布时 SSE 长连接优雅下线：preStop sleep 10s + 发"服务器重启"事件让前端主动重连
- HPA 的自定义指标链路（Prometheus Adapter）是最容易配错的件——先 CPU 弹性跑通再上自定义

## 3. 关键难点参考片段：降级链路的混沌验证

熔断/fallback 配了不等于生效——**混沌用例把它变成回归测试**：

```python
# tests/chaos/test_degrade_chain.py（CI 可跑的"软混沌"）
async def test_llm_outage_falls_back_to_local_model():
    mock_cloud.set_behavior(fail_rate=1.0)                  # 云端全挂
    async with agent_session() as s:
        result = await s.ask("hi")                          # 正常发起
    assert result.model_used.startswith("local/")           # 降级路由生效
    assert metrics.count("circuit_state", state="open") >= 1
    assert result.usage.cost_usd == 0                       # 本地模型零成本

async def test_redis_outage_fail_open():
    redis.stop()
    resp = await client.post("/api/v1/sessions", ...)       # 限流 fail-open 放行
    assert resp.status_code == 201
```

为什么难：降级路径平时不跑（覆盖率谎言）——只有主动注入故障才暴露"熔断配了但 fallback 模型没注册"这类配置性断裂。
