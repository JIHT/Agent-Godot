## 1. 知识点详解（每节五段：定义 → 大白话 · 举例 · 演进 · 易错点）

### 1.1 可观测三支柱：Logs · Metrics · Traces

**① 严格定义**：三支柱各答一个问题且互相索引——**Metrics**（数字，答"正常吗"：http_qps/p99、业务 agent_tokens_total{model,tenant}、tool_calls_total{tool,status}）；**Logs**（结构化 JSON 文本，答"发生了什么"：request_id/tenant_id/session_id 全程携带）；**Traces**（因果 Span 树，答"慢在哪/断在哪"：一次 craft 的 span 树=POST→query_engine→agent_loop.step→llm.stream→tools）。OTel 装配：FastAPI 自动 instrumentation + 手动 span（loop/tool 边界）+ **OTelBridge 订阅 EventBus 把 AgentEvent 转 span 属性**（核心包零 OTel 依赖——M00 纯库纪律兑现）。

**② 大白话**：**医院的三个检查科**。Metrics=体检指标单（体温 37.2、血压 120/80——一眼看出"正常吗"，但不告诉你为什么）；Logs=病历（按时间记录每件事——细节全但海量）；Traces=造影检查（一针显影剂跟完全程——**一眼看清 2.3 秒的请求里 1.2 秒卡在 LLM、610ms 花在 headless**）。三者互通的钥匙：request_id/trace_id——指标异常（p99 飙了）→点进对应 trace（慢在哪）→翻该 trace 的日志（当时发生了什么）。**同一事实的三种投影**，不是三套系统。

**③ 举例**：中间件埋 trace 上下文（可直接参考）：

```python
@app.middleware("http")
async def observability_mw(request, call_next):
    rid = request.headers.get("X-Request-ID", new_id())
    structlog.contextvars.bind_contextvars(       # 之后本请求所有日志自动携带
        request_id=rid, trace_id=current_trace().trace_id,
        tenant_id=get_tenant_or_none(request))
    with tracer.start_as_current_span("http.request") as span:
        span.set_attribute("http.route", request.url.path)
        t0 = time.perf_counter()
        resp = await call_next(request)
        hist.labels(route=request.url.path, status=resp.status_code
                    ).observe(time.perf_counter() - t0)
        return resp
```

**④ 演进**：printf 日志人肉 grep → 三支柱标准（Google SRE 推动）→ OpenTelemetry 统一 SDK（厂商中立）→ exemplars（metric 指向 trace）。

**⑤ 易错点**：
- P99 用 histogram **服务端分桶**计算——不是存全量延迟再排序（内存爆炸）
- **高基数 label 是 Prometheus 杀手**（session_id 做 label=时序爆炸）——高维信息进 logs/traces，metric label 只留 route/model/tenant
- SSE 的"延迟"是 **TTFB**（首字节，用户感知），连接时长不是延迟

### 1.2 分布式限流：Redis + Lua

**① 严格定义**：M02 令牌桶是单进程的——多副本下每 Pod 独立限=配额×N。分布式限流把计数搬 Redis，**Lua 保证"读-改-写"原子**（Redis 单线程执行脚本期间不插入其他命令）：

```lua
-- sliding.lua：ZSET 滑动窗口
ZREMRANGEBYSCORE key 0 now-window          -- 清窗外
count = ZCARD key
if count + cost > limit: return 0          -- 拒
ZADD key now now-seq; PEXPIRE key window; return 1
```

限流三个维度：租户 RPM/TPM（套餐配额）、用户并发会话数、全局 LLM 并发（成本护栏）。429 必带 Retry-After（M02 客户端重试链的另一半）。

**② 大白话**：**连锁店总部统一发票额度**。各门店（Pod）自己记限额=每家都以为自己有 100 万额度，总部（Redis）实际只想给整个连锁 100 万——计数必须**集中记账**；而"查账+开票"必须是**一手交钱一手开票**的原子动作（Lua 脚本），否则两个门店同时查账都看到"还剩 1 万"同时开票——超发。fail-open/fail-close 的选择：总部断联时门店**先赊账继续营业**（配额限流——短期超一点可接受）还是**停业等恢复**（成本护栏——LLM API 烧钱，宁可停）——按业务痛感定。

**③ 举例**：

```python
class RedisRateLimiter:
    async def allow(self, key, limit, window_ms, cost=1) -> RateDecision:
        ok = await self.redis.eval(self.script, 1, key,
                                   int(time.time()*1000), window_ms, limit, cost)
        if ok: return RateDecision.allow()
        wait = await self.earliest_release(key, window_ms)     # ZSET 里算 Retry-After
        return RateDecision.reject(retry_after=wait)
```

**④ 演进**：进程内锁→Redis INCR 固定窗（边界突刺：窗口切换瞬间双倍流量）→ 滑动窗口 ZSET（精确、内存 O(活跃)）→ 令牌桶 Lua（省内存允许突发）→ nginx/网关层。本项目：配额用滑动窗（计费精确语义）、全局保护用令牌桶（突发友好）。

**⑤ 易错点**：
- Lua 内避免 random（主从复制一致性）——成员唯一性用 INCR 序号
- Redis 挂掉的 fail 策略按业务分（上表），写清楚并测试
- ZSET 同毫秒成员冲突→计数偏小——序号后缀防撞

### 1.3 压测与容量规划

**① 严格定义**：Agent 平台压测的特殊性——**负载不是 QPS 而是"并发会话×每会话步数"**，下游 LLM 延迟秒级成本真金白银。三问：单 Pod 多少并发 SSE 稳定？工具执行洪峰打不打爆 CPU？**降级链路真的降级吗**（mock 云端全挂→熔断→fallback）？工具：k6 + **mock LLM 回放器**（录真实事件流按序重放——压"我们的系统"不烧"别人的 API"）。核心指标：SSE TTFB P99<1s、会话建立成功率、RSS 增长曲线（泄漏检测）。容量推算：压出单 Pod 200 并发→目标 5000→25 Pod+30% 冗余→HPA min10 max40。

**② 大白话**：**消防演习**。纸面上的消防设施（熔断配置/限流参数）和真着火时喷不喷水是两回事——演习（压测）要专门**点火**（混沌：把 mock 云端 LLM 设为 100% 失败），验证喷淋（熔断）启动、备用水源（fallback 本地模型）接管。回放器是演习用的"假火"：逼真（真事件流录制）但不烧真房子（不花 API 钱）。

**③ 举例**：k6 SSE 场景：

```javascript
export const options = { scenarios: { chat: { executor: 'ramping-vus',
  stages: [{duration:'2m', target:50}, {duration:'5m', target:200}] } },
  thresholds: { 'http_req_duration{endpoint:messages}': ['p(99)<1500'] } };
```

**④ 演进**：ab/wr（裸 HTTP）→ locust → k6（SSE 支持好）→ 混沌工程（Chaos Mesh 注入故障）。**从"测吞吐"到"验降级"是生产压测成熟的标志**。

**⑤ 易错点**：
- 别拿生产 API key 压（成本事故）——mock 或回放器
- 长连接压测 VU≠并发连接，对准"并发会话数"
- 泄漏看曲线不看瞬时：建断 1000 轮后 RSS 是否回落（hub 清理 bug 在此现形）

### 1.4 K8s 部署与无状态化改造

**① 严格定义**：部署拓扑：web（无状态多副本）/worker（Celery 独立，按队列积压扩缩）/beat（单副本+分布式锁防重）/godot-runner（headless 专用池，污点节点本地盘高 CPU）+HPA（CPU+自定义指标 sse_active_connections）+Ingress。**无状态化三改造**（compose→K8s 的真正工作量）：①本地文件状态外移（SQLite→MySQL 仓储双轨兑现 M00 端口-适配器；Godot 项目目录→共享存储/对象存储）；②**SSE 可漂移**——hub 环形缓冲搬 Redis Stream（补发不依赖原 Pod，**本项目最大改造点**）；③定时任务防重。

**② 大白话**：**从固定工位到热桌办公**。compose 时代每个员工有自己的抽屉（本地文件/内存缓冲）——工位没了东西就丢；K8s 多副本=员工随时换楼（Pod 重建），**抽屉里不能放任何东西**：文件寄存到共享仓库（PVC/对象存储）、取件记录放总部前台（Redis）——任何员工在任何楼都能凭号取件（连接漂移到任意 Pod 都能补发）。readiness/liveness 的分寸：readiness=“今天能上班吗”（没准备好不给派活但不辞退），liveness="还活着吗"（死了回收）——慢启动（加载模型 30s）用同一探针会被误杀循环重启。

**③ 举例**：hub 缓冲 Redis 化（连接漂移的关键 20 行）：

```python
class RedisSSEHub(SSEHub):
    async def publish(self, sid, ev):
        await self.redis.xadd(f"sse:{sid}", {"id": self._next_id(sid),
                                             "data": ev.json()}, maxlen=256)
        await self.redis.expire(f"sse:{sid}", 86400)
    async def replay_from(self, sid, last_id):
        return await self.redis.xrange(f"sse:{sid}", min=f"({last_id}")
    # 任意 Pod 都能补发任何会话 → 连接漂移自由
```

**④ 演进**：compose 单机→K8s 声明式（自愈/伸缩/滚动发布）→ Helm/Kustomize 参数化→GitOps。项目到 K8s+Kustomize（个人边界）。

**⑤ 易错点**：
- readiness≠liveness（慢启动被 liveness 误杀循环）
- 滚动发布 SSE 优雅下线：preStop sleep 10s+发"服务器重启"事件让前端主动重连
- HPA 自定义指标链路（Prometheus Adapter）最易配错——先 CPU 弹性再上自定义

## 7. 面试拷打（附详细参考答案）

**1. 三支柱各自回答什么？"同一事实的三种投影"怎么理解？**
答：Metrics 答"正常吗"（聚合数字，看趋势告警）、Logs 答"发生了什么"（离散事件细节）、Traces 答"卡在哪/断在哪"（请求内因果链）。"三种投影"的含义：一次 HTTP 请求同时产生三者——一个 metric 数据点（p99 直方图的一个样本）、若干条日志（带 request_id）、一棵 span 树——它们描述**同一个请求事实**，只是查询接口不同（趋势问题查 metric、定位到异常后查 trace、要上下文细节查 log）。工程推论：三者必须携带相同的关联键（request_id/trace_id），否则"投影"断裂——p99 飙了却找不到是哪个请求贡献的。

**2. 高基数 label 的危害？高维信息放哪？**
答：Prometheus 的时间序列数=label 值的笛卡尔积——session_id 做 label，每会话一条独立时序：10 万会话×每 15s 一个样本=时序数据库爆炸（内存/查询全崩），且这些时序几乎无聚合价值（单会话的 QPS 没有意义）。规则：metric label 只留低基数（route<100 种/model<10/tenant 千级可控）；高维信息（session_id/request_id/user_id）进 logs（按需过滤）和 traces（按 id 检索）——它们本来就是"按具体对象查询"的接口。判别一句话：**会拿来做聚合分组的才能进 label，只用来检索的进 log/trace**。

**3. SSE 的延迟指标为什么是 TTFB？**
答：SSE 是长连接流式响应——"请求完成时间"=整段回答生成完的时长（可能 60s），但**用户的感知延迟是"看到第一个字出现"的时间**（TTFB，首字节）。流式产品的体验契约：用户发出消息→1 秒内看到 Agent 开始打字→之后逐字流出（长的等待被"正在生成"的体验消化）。若把连接时长当延迟：所有数字 60s+，监控完全失真（p99 永远红）；压测阈值也错（k6 的 http_req_duration 对 SSE 全超时）。配套：分事件统计（tool_call_start 到 result 的工具延迟、message_end 的总时长）——**每段延迟对应各自的体验语义**。

**4. Redis+Lua 为什么原子？滑动窗口 vs 令牌桶的权衡？**
答：原子性来源：Redis 单线程执行命令，**一个 Lua 脚本作为整体执行期间不插入任何其他客户端命令**——脚本内的"读计数→判断→写计数"（check-then-act 竞态）对外表现为单条命令。没有 Lua 的等价实现要 MULTI/EXEC 事务+WATCH 乐观锁（复杂且失败重试）。滑动窗口 vs 令牌桶：滑动窗口（ZSET 存每个请求时间戳）**精确**（任意时刻的真实窗口内计数）但内存 O(活跃请求数)、严格拒绝突发（窗口满即拒）；令牌桶**省内存**（两个数字：存量+时间戳）、**允许突发**（桶里预存的令牌一次取光）但窗口语义近似。选型：计费相关的配额（租户 TPM——超了要准确收费）用滑动窗口；保护性限流（全局 LLM 并发——偶尔突发无害）用令牌桶。

**5. fail-open 与 fail-close 怎么按业务选？**
答：判断公式：**限流器失效时，"放行的代价" vs "拒绝的代价"谁大**。配额限流（租户 RPM）：放行代价=个别租户短期超额使用（可事后补账）——小；拒绝代价=所有用户不能用产品——大→**fail-open**（放行+告警）。成本护栏（全局 LLM 并发）：放行代价=无上限烧 API 钱（直接经济损失）——大；拒绝代价=新会话等待（可排队）——中→**fail-close**（拒绝+降级到本地模型）。还有第三态：fail-degraded（降级到更粗粒度的本地近似限流——单进程兜底）。关键工程纪律：**每个限流器的 fail 策略显式声明并测试**（混沌用例：停 Redis 断言行为）——默认行为（通常是挂掉）从来不是策略。

**6. Agent 平台压测与普通 Web 压测的三个差异？**
答：①**负载模型不同**——不是 QPS 而是并发会话×每会话步数×每步工具执行：一个会话占用连接数分钟（非毫秒），资源画像=长连接协程+子进程（headless）而非短请求；②**下游太贵太慢**——真实 LLM API 延迟秒级、按 token 真金白银——压测必须 mock/回放（压自己的系统不烧别人的钱），否则一次 200 并发 10 分钟压测=四位数账单；③**要验降级不只验容量**——普通 Web 压吞吐和错误率就完；Agent 平台的核心生存能力是降级链（云端挂→熔断→本地接管），压测必须包含故障注入场景（degrade_chain），这也是"压测"与"混沌工程"在此合流的原因。

**7. 回放器解决什么？怎么造？**
答：解决"真实下游不可用于压测"：真实 LLM 又贵又慢又不稳定（压测结果抖动来自下游而非被测系统）。造法：①**录制**——开发期真实会话的事件流（prompt 的 hash→事件序列+时间戳）存 JSONL；②**回放**——压测时起一个 OpenAI 兼容的假服务：请求进来按 prompt hash 命中→按录制的时序 yield 事件（保留原始延迟分布，逼真模拟慢）；未命中→固定模板回答（log 记录新 prompt 供扩充语料）；③**故障注入模式**——set_behavior(fail_rate=0.5/latency=+2s)——降级链路演习的假火。收益：可重复（回归对比）、免费、可控（精确控制延迟/失败率画像）。

**8. K8s 无状态化三改造？hub Redis 化为什么是关键？**
答：三改造：①文件状态外移——SQLite→MySQL（M00 仓储双轨的最后兑现）、Godot 项目目录→共享存储/对象存储按需物化；②SSE 连接可漂移——hub 环形缓冲从进程内存搬到 Redis Stream（XADD maxlen+TTL），补发能力不再绑定 Pod；③定时任务防重——beat 单副本+分布式锁。hub Redis 化是关键的原因：它是**唯一阻碍"任意 Pod 服务任意会话"的状态**——用户重连经负载均衡落到新 Pod，新 Pod 必须能补发该会话的历史帧：内存版做不到（缓冲在旧 Pod 里，旧 Pod 已死）；Redis 版任意 Pod XRANGE 即得。这直接解锁：滚动发布不丢会话（M19 面试题 10 的多区域方案同源）、HPA 扩容后新 Pod 立即可用、Pod 崩溃用户无感。

**9. readiness 与 liveness 的语义差？慢启动怎么配？**
答：readiness=“**能接活吗**”（不 ready 就从 Service 摘除流量，但 Pod 保留——加载完自动回来）；liveness="**还活着吗**”（失败=重启容器）。语义不同的原因：摘流量是温和的（不派新活），重启是暴力的（正在处理的活被杀）。慢启动（模型加载/索引预热 30s）的配置：readiness 用慷慨的 failureThreshold（如 30 次×2s=60s 宽限）或 startupProbe（专门的启动期探针，通过前不跑 liveness）；liveness 用宽松阈值且**绝不检查重依赖**（DB/Redis 短暂抖动不该触发容器重启——重启解决不了外部问题反而雪崩放大：全部 Pod 同时重启=服务全停，级联故障经典）。

**10. 开放题：跨可用区部署，GB 级 Godot 项目文件放哪？**
答：三方案 tradeoff：①**RWX 共享存储（NFS/EFS）**——所有区读写同一份：简单但跨区 IO 延迟高（随机读写 headless 编译要秒级文件访问，体验崩）且单点；②**对象存储+按需物化**——项目 zip 存 S3，任务调度到某区时**拉取+解压到本地盘**（物化），完工后检查点 diff 回传 S3：读性能好（本地 NVMe）、天然多区（数据在 S3 全区可拉）；代价=物化延迟（10~60s 冷启动，用预热缓存缓解——常用项目物化副本保活）；③**跟随主副本**——项目固定归属某区（tenant→region 映射），跨区用户承受延迟：最省事但违反"任意区可服务任意租户"。推荐②：与 M09 检查点机制天然契合（检查点本来就是文件级快照=增量上传单元），冷启动用 M22 沙箱的 fresh() 同款机制。核心原则：**计算跟着数据走（本地物化），数据跟着持久层走（对象存储）**——分布式文件系统的本地性原理。
